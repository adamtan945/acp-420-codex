依賴方向與責任角色分開讀

服務目錄描述服務本身、依賴關係與責任；incident 或 change 的 Affected services 只建立工作關聯。新 Services 採 Assets 模型，編輯服務需相應 schema 權限，不能只看 JSM 專案角色。

用一個例子理解

虛構借書入口 depends on 登入服務，登入服務 depends on 身分資料庫。教學 incident 引用登入服務，可用來看影響脈絡；從另一張 change 移除此欄位值，不會把登入服務從目錄刪掉。

03.02 服務目錄、責任角色與服務分級

適用範圍、版本用語與案例前提

本課適用 Jira Service Management Cloud，以 company-managed 服務專案為主要情境。新版文件可能寫 service space、work item、work type；考綱仍使用 project、issue、issue type。

教材保留兩套名稱，不把新名稱直接代入 JQL。所有人物、工單和設定數值都是原創教學案例。

從「哪張單壞了」走向「哪個服務受到影響」

服務（service）是對業務或使用者提供價值的系統、平台或能力，例如借書入口、帳號登入、館際配送。一次 incident 可以影響多個服務；同一服務也可能有許多 incident 或 change。把服務記錄放在服務目錄中，能把負責團隊、重要程度與依賴關係帶到處理現場，而不用每張工單重寫。

官方來源：What are services?

先備詞彙：service catalog 是服務目錄；tier 是業務關鍵程度；owner team 是長期維護責任團隊；responder 是事件中需要回應的人或團隊；change approver 是變更核准人；stakeholder 是需要掌握消息的人；

reference／relationship 是服務間的參照關係。

03.02.01 啟用 Services，並辨識目前的資料模型

考綱要求從 Features 啟用 Services。先由具相應權限的 Jira admin 到服務專案 Space settings → Features 查看。官方側邊欄文件說明 Services 適用 ITSM spaces；

若入口沒出現，先確認專案類型、方案、rollout 與存取權，而不是立刻把所有使用者提升權限。

官方來源：Add Services, Alerts, and On-call to your sidebar

2026-10-05 的目前 Services 文件描述新的 Assets-backed 體驗：Services 資料使用 Assets 的 Software Registry 和 Business Portfolio 等預先提供的 schema，主要入口為 Operations → Services。

服務編輯權限由相關 Assets schema／object type 權限控制，不再能簡單推論「我是 JSM project admin，所以一定可編輯所有服務」。這是目前介面差異，不改變考綱要你管理服務脈絡的目的。

官方來源：Configure Services: settings, permissions, and references

官方文件也指出 Services 在 2026 年 7 月 31 日後不再提供於 Free，Standard／Premium／Enterprise 可使用；change management 等進階能力另有方案限制。不要把「可建立服務目錄」誤讀成「每個進階事件或變更功能都在相同方案內」。

官方來源：Configure Services: settings, permissions, and references

官方來源：Add or remove a service from the affected services field

03.02.02 將服務加入 incident 或 change，只改工單關聯

在事件工作項目上找到 Affected services，加入受影響的既有服務。這讓處理人員看到該服務的依賴、owner 等脈絡。Change 也可在相應欄位選取預計影響的服務；若不再相關，可移除欄位中的該項。從工單移除關聯，不等於刪除整個服務目錄物件。

官方來源：service-incident

官方來源：Add or remove a service from the affected services field

原創例子：教學「借書入口」依賴「登入服務」，登入服務又依賴「身分資料庫」。資料庫故障時，事件最初可以列資料庫，調查確認借書入口確實受影響後再加入它。服務圖顯示的是已建好的參照；沒有畫出某條依賴，不足以證明它不存在，也不能直接把所有可連到的服務都宣告故障。

新版 Services 文件特別指出，單純加入 service 到 incident，不會自動通知 owner team，也不會自動設定 incident priority。需要通知的團隊應明確加為 responders；若要依 tier 設 priority，需建立相應 automation。

加入 service 到 alert 本身也不改 alert routing。這些行為要和舊版說明區分，不能用一張服務連線圖代替通知測試。

官方來源：service-incident

03.02.03 Service／Service Affected 與目前 Affected services 欄位

考綱用詞含 Service、Service Affected。現在官方 ITSM work type 文件主要使用 Affected services。教材把它們放在「讓工作項目參照服務脈絡」這個共同目的下理解，不假定所有同名欄位都屬同一原生型別。

管理員必須核對實際 field ID、型別及 request type 所用 work type；自行建一個文字欄叫 Service，不會得到服務目錄的參照功能。

官方來源：service-fields

在 Space settings → Request management → Request types 選擇教學 incident 或 change 類型，檢查 Work item view 中需要的 Affected services。

若欄位缺少，先確認底層 work type／screen 是否包含它，必要時由有權管理員補上適當原生欄位。這裡是 agent 端顯示配置，不代表客戶 portal 可直接操作同一欄位。

官方來源：request-customize

官方來源：service-approval

重要限制：目前 Cloud KB 指出，沒有 Jira 授權的 portal customer 即使看見 request form 的其他欄位，也不能直接查看或設定原生 Affected services。

若需要客戶選服務，可以另設適當 Assets selector 並以 automation 轉換，但這是需額外設計、授權與測試的延伸方案，本課不把它當成原生欄位直接可用。

官方來源：service-portal-limit

03.02.04 服務內容：關係、分級與四種責任

資料中的角色用途不同；實際通知仍須核對規則與功能。

服務關係回答「這個服務依賴誰、誰依賴它」。在新的 Services details 可編輯 Software Registry references／Business Portfolio references 等既有參照屬性；選取要參照的服務再儲存。

先把箭頭文字寫清楚，例如「借書入口 depends on 登入服務」。不要只畫無方向連線，讓下游與上游混淆。新的參照型別標籤不應被推論為自動禁止刪除或自動反向連結。

官方來源：Configure Services: settings, permissions, and references

Tier 回答「此服務失效對業務有多大影響」，通常 Tier 1 最關鍵，數字增大代表較低關鍵程度。它不是當前某張 incident 的 Priority，也不是 SLA 目標時間；可以作為訂定反應政策的依據，但不會自己執行政策。

官方來源：What are service tiers?

Owner team 對服務長期負責，responder 是發生事件時需要處理或被通知的人，change approvers 審核相關變更，stakeholders 接收影響與進度消息。四者可以有部分重疊，但沒有必須完全相同。

圖書館可以由「平台組」擁有登入服務，由當班工程師回應，由變更審核組核准上線，讓館務主管接收進度。

官方來源：What are services?

官方來源：service-create

目前建立服務時 Name、Service type、Tier 等核心資料需正確填寫，Owner team、Change approvers、Responders、Stakeholders 可依情境補充。

編輯時從 Operations → Services 開啟教學服務，在相應屬性選正確團隊／人員後 Save。不要選真實人員來觀察通知效果。

官方來源：service-create

僅在服務資料中指定 change approver，不等於所有工作流程已自動加上核准關卡。Request type 的 workflow 必須有相應 approval 設定，並在需要時啟用 Include approvers from service／Affected services 來源。

04.04 會完整說明核准流程；本課要求你能辨認服務的核准人資料與工作流程執行之間仍有配置關係。

官方來源：service-approval

03.02.05 用 tier 驅動 automation 與警示反應

「Tier 1 要更快通知」是業務需求，不是一個只要填 Tier 就會發生的效果。可以設計：Work item created 事件啟動規則 → Affected services condition 檢查是否有 Tier 1 → 執行設定 Priority 或通知等適當動作。

這裡的 trigger 是建立事件，tier 是條件。若建立之後才選服務，就需選能涵蓋後續欄位變更的事件或另有規則；只有建立時檢查，可能錯過後加的 service。

官方來源：What are service tiers?

官方來源：Jira automation conditions

官方來源：service-incident

Affected services condition 可依 tier、服務名稱或依賴服務檢查，但文件限定在 ITSM 專案且工作類型含適當欄位。警示反應可沿用 02.03–02.04 的 priority 映射、responders、routing 與 escalation；

需要明確設定這些控制點，不能假設 alert 看見 Tier 1 就自動變成 P1 或通知 owner。

隔離練習：教學入口的依賴與責任

前提：具合適方案的獨立 ITSM 教學網站、既有安全的 Services 環境及測試團隊；服務編輯者已被授予必要 Assets 權限。所有 owner、responder、approver、stakeholder 都使用核准測試名單。

若目前 rollout 不提供新 Services 畫面，先記錄版本差異，以紙上模型完成同一概念。

  1. 由管理員確認 Features／Operations → Services 可用及自己的編輯權限。在教學服務清單確認「借書入口」「登入服務」「身分資料庫」三個原創服務
  2. 開啟借書入口，設定 Tier 1 及教學 owner team；分別填入教學 responders、approvers 與 stakeholders。儲存後重新開啟確認，不以臨時未儲存的表單當結果
  3. 加入借書入口 depends on 登入服務；登入服務 depends on 身分資料庫。從服務圖核對方向及兩跳依賴，不創建新的 schema 結構
  4. 建立無敏感資料的教學 incident，在 Affected services 加入登入服務。觀察依賴脈絡；另做教學 change 並加入同一服務，確定兩張不同類型工單引用同一服務資料
  5. 從 change 移除該服務欄位值，重新開啟 Services 確認服務仍存在。這測試關聯移除與物件刪除的差異
  6. 用無 Jira 授權的教學客戶檢查 portal，不要求他直接選原生 Affected services；記錄與 agent 畫面不同的結果
  7. 紙上設計或在核准的教學規則中配置「建立→Tier 1 條件→記錄訊息」，與另一個 Tier 3 案例比較。只有符合者應通過分支；未選服務的案件應有明確預期
  8. 檢查規則未啟用任何真實通知，再記錄要把 Tier 1 映射為事件／警示優先度時還需要哪幾項明確配置

教學的驗收不是「建了三個名字」而已；應能指出資料位置、關係方向、不同責任，以及工單引用後的可見結果。

重點回顧

服務目錄讓事件與變更取得共同脈絡。分清服務本身、工單關聯、依賴方向、Tier 和各責任；讓政策成真仍需適當 workflow、automation 與 alert 配置。

常見陷阱

  • 原生 Affected services 不是任何 portal customer 都能直接填寫的欄位
  • 設 owner、tier 或關係不等於已通知、已提高優先度或已建立核准關卡
  • 服務圖僅呈現已建的關係，缺少連線不能證明沒有依賴
  • 新 Services 的編輯權需核對 Assets，不能只看 project admin

觀念釐清

考綱中的服務角色與分級概念仍要學；目前 Assets-backed Services 的管理入口與權限是版本註記。理解資料如何在工單上被使用，不要求在 03.01 擴張為 schema 設計課。

文件限制與待實機核對

舊版部分警示文件描述與服務 owner 的自動通知關聯；新的 Services 專文明確要求 responders／automation。本課以新版 Services 情境為目前操作依據，不宣稱所有歷史網站相同。

Service／Service Affected 舊標籤與現場欄位的對照、通知及核准流程尚未實機測試。
