推薦範圍不等於閱讀權限

文章建議在顧客填 Summary 時提供可能有用的內容，label 可縮小推薦範圍。推薦條件與閱讀權限是不同控制；帶正確標籤的受限文章仍不可因為推薦設定而開放。

用一個例子理解

三篇假文章中，A 是「投影機重啟」並帶 lab-projector，B 是「掃描器重啟」帶 lab-scanner，C 帶 lab-projector 但受限。投影機入口只用 lab-projector 篩選後，仍要用 customer 驗證 C 的直接網址不可讀。

06.02 文章建議與內容組織

一位顧客正準備填寫「會議室螢幕無畫面」請求，系統在他輸入摘要時顯示一篇輸入來源檢查文章。如果這篇文章正好解決問題，就省下一次等待；如果顯示的是離職程序，反而增加困惑。本課教你把文章建議放在對的 request type，並用 labels 限定相關內容，同時維持真正的文章權限。

名詞與先備條件

Knowledge base article（知識庫文章）是一份可供重複使用的說明；label（標籤）是加在文章上的關鍵字；article suggestion（文章建議）是在顧客填 request form 時出現的相關文章。

Request type（請求類型）是顧客選擇的求助入口，Summary（摘要）是他用一句話描述需求的欄位。

要練習這一課，先有一個獲准的 JSM 測試服務專案、同站點的已連結 Confluence 知識來源，以及至少幾篇已發布、對測試客戶可讀的文章。管理建議設定使用 space admin；編輯文章及 labels 需要相應文章編輯權。只有來源已連線，不足以保證顧客讀得了，權限判斷見 06.01。

S01S02S03

支援理解的補充 如何準備可用文章

這段補充讓零基礎讀者能完成練習，不新增官方考綱子目標。已有可用文章時可以直接接下一節。

在服務專案 Knowledge base 的 external knowledge base 選 Create article，選擇已連結的示範 space，撰寫後 Publish。未準備好發布時可保留 draft（草稿）；草稿不是已可供顧客使用的完成內容。

範本可協助形成一致結構，但不會替你驗證現場設備和操作。S04

原創文章「示範螢幕無畫面時先檢查輸入來源」可以依序寫：適用哪些示範設備、開始前要準備什麼、三個安全步驟、成功時會看到什麼、仍未恢復時要如何提出請求。不要把內部工單原文直接公開，也不要放公司密碼或真實人員資料。能讓初學者安全完成並知道何時停止，比大量不相關關鍵字更有價值。

在文章的 Labels 面板加入一致的標籤，例如 demo-room-display。另一篇「示範投影線材檢查」也使用同標籤；「示範麥克風電池」使用 demo-room-audio。標籤協助文章分類、搜尋與建議，不需要為同一主題建立很多拼寫近似但不同的標籤。S03

06.02.01 在指定入口啟用文章建議

到 Space settings 的 Knowledge base，找到 Control article suggestions。針對「練習：螢幕無畫面」request form 開啟 Allow suggestions?。

目前部分導航把 Knowledge base 放在 Channels & self service 之下；以功能名稱尋找相同設定。S01

這個開關是按 request form／request type 設定，不是看到知識庫已連線就等於所有入口都採相同推薦行為。顧客在 portal 提出請求、輸入 Summary 時，系統才會顯示可能有用的文章。

測試應真的以 customer 身分進到該入口並輸入相關摘要，而不是只在 Confluence 搜尋文章。S01

哪些入口值得開？原創判斷例子：「螢幕無畫面」有安全自助步驟，可以在送出前提供；「借用已核定的攝影機」可能仍需必須的實體安排，文章建議則可用來說明領用前準備。文章是否能完全減少請求，不是啟用的唯一價值；也可以讓提出的請求資訊更完整。

目前官方特別指出：若知識庫連到不同 Confluence site 的 spaces，這種 portal article suggestions 不會顯示。因此「能在服務知識庫使用來源」與「支援這個表單內建議功能」要分開檢查。沒有顯示時先確認來源架構，不先讓文章公開。S01

06.02.02 用 label 縮小推薦範圍

在同一個 request form 的 Only show articles labeled 欄位加入 demo-room-display，讓這個入口的建議專注在符合標籤的文章。先把標籤加到文章，再在入口設定選用；只在設定處寫下標籤名稱，不會替所有文章自動補標籤。S01S03

想像三篇測試文章：A「輸入來源」有 demo-room-display；B「線材檢查」有 demo-room-display；C「麥克風電池」有 demo-room-audio。入口限定 display 後，A、B 才是符合此標籤條件的候選；

至於實際顯示與排序還涉及搜尋內容與相關性，不能保證每次 A、B 都必定同時出現或固定排序。

本課的示範只使用單一篩選標籤，避免把未確認的多標籤 AND／OR 語意當成考點。若實際需要多標籤組合，先查當前介面說明並在隔離站建立正反例驗證，再形成配置決策。本次文件核對不推論未說明的比對優先順序。

內容篩選與存取限制要分清楚

B 可讀但可被篩掉；C 標籤對也不能推論可讀。

Label 決定「此入口推薦哪些主題」，不是「誰有權看文章」。一篇沒有 demo-room-display 的文章可能不在這個表單的建議範圍，卻仍可透過別的入口、搜尋或已有連結由具權限的人讀到；一篇有正確標籤但受限的文章，也不會因為標籤命中就自動授予顧客權限。S01S02

因此，若需求是「內部維修紀錄只給服務人員看」，應設真正的 knowledge base／Confluence 權限。把它改成一個沒人知道的 label，或從所有建議清單移除，不能達到保密目的。設計時可用兩句話分開記錄：「哪些人可讀」與「在哪個入口容易被找到」。

分享文章有不同時機

顧客送出前的 article suggestions 是自助路徑；

顧客已提出請求後，agent 可以從 Knowledge base 文章使用 Copy article link，或在工作項目的 Knowledge base 區找到文章，透過 Share as comment 把連結放進回覆，再補充適合此案件的說明後送出。

分享仍受文章權限限制，複製連結不會增加對方閱讀資格。S05

選擇時機的原創例子：若只是忘記選正確訊號源，自助建議可能足夠；若顧客已清楚說完成所有檢查仍失敗，agent 不應只重貼同一篇文章而不接手。這種判斷以顧客已做的事與文章適用範圍為依據。建立自動分享規則是 08 域的另一層工作，本課不把舊版 automation 文件當成必要設定步驟。

隔離練習 用三篇文章驗證推薦與權限

前提：三篇自寫虛構文章位於獲准的同站點測試 space，測試 customer 有預期權限，沒有真正客戶或正式內容。若需要修改權限或公開內容，先取得該範圍批准；不因練習而分享內部資料。

  1. 準備 A「示範輸入來源」、B「示範線材」、C「示範音訊」三篇文章，確認各篇已發布與預期可讀。
  2. 在 A、B 加 demo-room-display，在 C 加 demo-room-audio。記錄標籤拼寫，不用繁簡混用或空格變體製造無意差異。
  3. 對「練習：螢幕無畫面」開啟 Allow suggestions?，先不限制 label。以 customer 輸入與螢幕有關的 Summary，記錄候選文章。
  4. 設定 Only show articles labeled 為 demo-room-display，再以相同身分與相同摘要測試。比較是否排除不符合 label 的內容；不要要求搜尋排序一定不變。
  5. 直接以客戶可用的 C 文章連結打開。若原本有權閱讀，標籤篩選不應被當作撤銷其閱讀權的手段；記錄這個不同途徑的觀察。
  6. 如果管理員批准，在另一篇虛構測試文章加真正的頁面限制但保留相同 label。驗證 label 不會取代權限；不把受限文章內容放入公開回覆。
  7. 在一張示範請求中由 agent 插入合適文章連結並加入原創簡短說明；若沒有寄信授權，就停留在草稿，不實際送出。
  8. 若建議沒有出現，逐項檢查來源是否跨站、開關、標籤、文章發布、可見權限與所輸入摘要，記錄實際原因，不先修改整個站點存取。

驗證狀態：以上為官方文件支持的隔離練習設計，未在租戶實際執行；尤其不宣稱搜尋排序、多標籤運算或任何客戶可見結果已通過測試。

摘要

用 request type 決定在哪個求助情境提供建議，用 labels 限定相關主題，再以實際顧客身分測試。文章內容品質、可見權限、來源架構與搜尋相關性都影響是否真正幫助顧客。

常見陷阱

  • 把 label 當成機密文章的安全限制
  • 只寫篩選標籤，卻忘記加到文章
  • 用管理員的搜尋結果代替顧客表單測試
  • 把跨站來源可連結誤認為每種功能都支援
  • 保證所有候選文章都會以固定順序出現

觀念釐清

「可閱讀」「在此入口符合建議條件」「這次搜尋實際顯示」是三個問題。先用權限決定第一個，再用配置與相關性判斷後兩個。
