資格連結誰、支援哪個產品

Product 表示支援項目，entitlement 表示某顧客或組織對該項目的支援資格。Required 欄位可限制這張 request form 的提交，但不能當成所有渠道的保護。新網站的此功能已搬至 CSM，要先確認產品環境。

用一個例子理解

虛構「教學掃描器」只給北館測試客戶 A 資格，B 沒資格，C 只有「教學投影機」資格。當教學掃描器入口要求 Entitlement 時，要用三個獨立身分比較清單與能否提交，不能只測 A 成功。

03.03 產品與支援資格

適用範圍、版本用語與案例前提

本課適用 Jira Service Management Cloud，以 company-managed 服務專案為主要情境。新版文件可能寫 service space、work item、work type；考綱仍使用 project、issue、issue type。

教材保留兩套名稱，不把新名稱直接代入 JQL。所有人物、工單和設定數值都是原創教學案例。

產品是「支援什麼」，Entitlement 是「誰有這個支援資格」

假設晨光維護團隊支援兩個產品：「教學借書機」與「教學盤點服務」。同樣能進客服入口的兩位客戶，不一定都購買或被授權使用兩個產品。Product 記錄支援對象；entitlement（產品使用／支援資格）把某位客戶或某個客戶組織與該產品連起來，並可附上服務等級、期限等詳細資訊。

這不是購買 Jira agent 授權，也不是把客戶加成專案管理員。

官方來源：About products and entitlements

先備詞彙：product 在這裡是你服務客戶所提供的產品／服務，不是 Atlassian 的 app access；entitlement detail field 是資格的背景欄位；Entitlement field 是請求上讓客戶選擇已有資格、讓 agent 看見相關脈絡的欄位；

required 是在該提交表單必須有值。

03.03.01 先分考綱環境與新網站的 CSM

考綱 V2 April 2025 使用 JSM Products and Entitlements，並要求由 Features 啟用。

適用的既有 JSM 網站可由管理員到 Space settings → Features 查找 Customer service management 與 Products and entitlements；官方 JQL 說明也仍列出這兩項功能開關作為相關功能前提。

官方來源：jql-current

但現在必須先辨認網站世代：官方文件明確說明，2025 年 10 月 Service Collection 推出後，新網站的 customer-service 功能移往 Customer Service Management（CSM）。因此新的教學網站可能要在 CSM 操作；

找不到舊 JSM 開關，不代表考綱目標不重要，也不表示一定是權限壞掉。先記錄目前 app、介面與方案，再採適用文件。

官方來源：About products and entitlements

官方來源：csm-entitlements

本課保留完整的 JSM 考綱概念與適用舊介面步驟。CSM 的 customer experience／Forms 入口不是舊 JSM request type 的同義路徑；若使用 CSM 練習，必須另以 CSM 文件驗證，不把下方按鈕位置機械搬過去。

03.03.02 先有產品，再把資格授給客戶或組織

在適用 JSM 環境的 Products 入口選 Add product，輸入原創教學產品名稱並新增。管理員與 agents 可新增／編輯產品；建立 entitlement detail fields 則要 Jira admin。

Detail fields 的定義會套用網站上所有產品／客戶的資格資料，不只當前服務專案，因此名稱與類型要先設計。

官方來源：About products and entitlements

官方來源：Create product entitlements for your customers

到 Customers 或 Organizations，開啟目標檔案，選 Create entitlement，明確指定是給個人還是整個 organization，再選對產品。給 organization 的資格會讓其中所有客戶與該 entitlement 關聯；

所以「只想給某一人試用」時，不應隨手選整個組織。建立後回到檔案確認資格及詳細欄位。

官方來源：Create product entitlements for your customers

原創例子：A 和 B 是「教學北館」成員，北館擁有「教學借書機」資格；C 個人擁有「教學盤點服務」資格。A、B 可以使用北館的借書機資格，C 的個人盤點資格不會因此自動授給 A、B。組織成員改變也可能改變享有組織資格的人，因此成員管理和資格管理應一起驗證。

如果 detail field 叫「到期日」，填入日期只是保存資料。不能僅因欄位名字含到期，就假定系統已自動停用資格或拒絕所有後續請求；這種期限政策是否自動執行需要對應產品能力或另設規則，應現場測試後才宣告。本課示例不建立金流、契約或自動取消服務行為。

03.03.03 把 Entitlement 放到 request type，讓脈絡跟著工單

先有 Products、客戶／組織資格和需要的 details，再在 request type 的 Request form／Work item view 加入 Entitlement field。

若想讓 agent 在工作畫面看到「教學支援等級」等詳細資訊，由 Jira admin 在 entitlement details 的 Show on work item view 開啟要顯示的欄位。

這是兩個不同動作：讓請求選到哪個 entitlement，以及決定顯示哪些 entitlement details。

官方來源：Show product entitlement details on work items

對有資格的 customer，request form 的 Entitlement 選項來自其已有資格。選到正確產品後提交，agent 在工作項目能讀到對應產品與支援脈絡。不要只把 Product 名稱打在 Summary 裡，因為那只是文字，沒有建立與資格紀錄的關係。

官方來源：About products and entitlements

官方來源：Show product entitlement details on work items

具體例子：A 在「教學借書機支援」表單選北館的借書機 entitlement，描述讀卡異常。Agent 開單後能辨認支援產品和教學服務等級，不必重新猜測是不是盤點服務。若 A 有兩種產品資格，應讓他選與問題相關的一個，不能把「任何有效資格」當成所有產品通行證。

03.03.04 Required 的效果與它的安全邊界

驗證顧客自己的清單；agent 能看全部不代表顧客能選全部。

若把 Entitlement 設為 request form 必填，沒有任何可選 entitlement 的客戶會因無法填入必要值而不能提交這個表單。這可讓限定資格的服務入口擋下明顯不符合條件的提交。啟用前，要確認合法客戶已有正確資格，否則你會把真正應服務的人也擋在門外。

官方來源：About products and entitlements

官方來源：Show product entitlement details on work items

「必填」先證明的是此表單需要選到可用 entitlement，不應未經驗證就說它能辨認任意產品組合、期限契約或涵蓋所有請求管道。若需求是「只有借書機資格可送這個借書機表單」，要用僅有盤點資格的 C 做反向測試，確認選項與表單限制是否精確符合產品範圍。

若現場只提供一般 entitlement 選項而無對應產品限制，應另設明確流程或校驗；不能把 Required 本身當成完整的產品授權引擎。

同樣，email、API、chat、agent 代建是否受相同必要欄位與驗證影響，需要逐管道查核。本課不聲稱 request form 必填等同全管道的系統安全控制，也不要求為了測試去接真實 email 或 API。權限仍依第 01 領域的角色、客戶存取與資料安全共同運作。

隔離練習：有資格、沒資格、資格是另一產品

前提：獨立教學網站，先確認是仍提供功能的 JSM 環境或已移至 CSM。以下按 JSM 步驟；只有無個資的 A、B、C、D 測試帳號與測試 organization。建立資格可能影響組織全部成員，只操作空白教學組織，不把真實客戶加入。

  1. 在適用 JSM 的 Features 核對兩項功能已可用；若功能已移至 CSM，記錄差異，先以紙上資料完成概念，不猜按鈕或提升權限
  2. Products → Add product 建立「教學借書機」與「教學盤點服務」。核對名稱代表服務對象，沒有變更任何 Atlassian app license
  3. 為「教學北館」建立借書機 entitlement，A、B 是其成員；為 C 個人建立盤點 entitlement；D 不給任何 entitlement
  4. 若要顯示脈絡，Jira admin 建立或使用既有的「教學支援等級」detail field，填入測試值，開啟 Show on work item view
  5. 在教學 request type 加入 Entitlement，先不設必填。A 打開 portal 檢查自己的可選項；C 另行登入，核對可選資格不同
  6. 改為 Required 後，用 A 提交一單。預期可以選其適用 entitlement 並成功提交；agent 端核對產品及 detail 值
  7. 用 D 嘗試提交同一表單。預期沒有資格可選，必填欄位使表單不能提交。記錄文字錯誤，不以真正客戶測試
  8. 用 C 測「另一產品資格」情境。記錄能選到什麼、是否可提交，對照業務要求。這步專門驗證 Required 是否只是存在性檢查，不能預先宣告具備全部產品限制
  9. 回到 agent 畫面，確認 Show on work item view 的教學 detail 確實出現。將該顯示開關關閉再開啟，辨認只是顯示變更，沒有因此撤銷客戶資格

這組正反向測試用來證明「可用資格選項→表單必填→工單顯示」三段各自的效果；沒有實機環境時保留預期，不寫成已完成驗收。

排錯：明明應該有資格卻無法提交

先核對登入帳號與客戶檔案，再核對是個人 entitlement 還是組織 entitlement，以及客戶是否真的是該 organization 成員。接著看產品是否正確、request type 是否使用真正的 Entitlement 欄位、是否有必填設定與可選項。

Agent 看不到細節則另查 detail field 的可見權與 Show on work item view，不要把顯示問題誤判成資格不存在。

重點回顧

先辨識 JSM／CSM 環境，再建立產品、授予個人或組織資格，最後在請求上選取並顯示資格。必填的效果必須用有資格、無資格與另一產品資格三種案例驗證。

常見陷阱

  • 有 customer 帳號不代表有所有產品 entitlement
  • 加到整個 organization 的資格範圍比單一客戶大
  • 到期日 detail field 不自動等同自動停用政策
  • Required 不應被擴大解釋為所有管道及所有契約限制的通用安全控制

觀念釐清

建立產品、建立 entitlement、把 Entitlement 欄位放上表單、顯示 detail fields 是四個相互依賴但不同的設定。只有最後一步有畫面，不代表前面的資格資料正確。

文件限制與待實機核對

新網站的 CSM 入口與舊 JSM Features 不同，課文不宣稱已在任一租戶測試。特定產品選項限制、期限自動處理、email／API／chat 行為在未實測前均保留為明示限制，不以推測補成產品承諾。
