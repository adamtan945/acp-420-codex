04.01 請求類型與欄位呈現

一家公司的同仁想借投影機。他不應先學會內部的工單分類，才能問「我要借投影機」。本課教你把顧客的用語接到 Jira 的工作處理方式：讓顧客找得到入口、填對資料，並讓服務人員收到可處理的工作項目。這也是 request type 最重要的用途。

先認識這些詞

Jira 是用來追蹤工作的系統；Jira Service Management（JSM）在它之上提供服務請求、客戶入口與服務團隊的處理功能。服務專案（service project，新版介面稱 service space）是一個服務團隊管理請求的範圍。客戶（customer）提出需求；服務人員（agent）在內部處理需求；專案管理員（project admin，新版稱 space admin）調整該專案設定；Jira 管理員（Jira admin）管理跨專案設定。

請求（request）是顧客看到的求助紀錄；工作項目（work item，考綱稱 issue）是團隊處理同一件工作的內部紀錄。請求類型（request type）是顧客選的服務入口。工作類型（work type，考綱稱 issue type）決定底層工作設定。欄位（field）是一格資料，例如 Summary（摘要）；工作流程（workflow）是狀態與狀態間轉換的組合。入口群組（portal group）則是把入口排成好找的分類。

本課以 company-managed（公司管理型）服務專案為主。Space settings 是目前文件名稱，較舊介面可能顯示 Project settings。以下是文件核對的操作教學，沒有聲稱在你的租戶完成實測。

04.01.01 一種工作可以有多個顧客入口

設想「借投影機」與「借會議麥克風」都要經過收到申請、確認庫存、交付、歸還。它們可以是兩個 request types，同時使用同一個「設備借用」work type。顧客看到不同的名稱與說明，團隊仍採用一致的工作流程。一個 request type 同一時間只連到一個 work type；在適用的 workflow scheme 中，該 work type 再連到一個 workflow。S01

因此，改 request type 名稱不等於新增 work type，也不會自動產生另一套 workflow。反過來，改共用的底層設定可能影響多個入口。先畫出關聯，再決定修改哪一層，能避免為了改善一張申請表，連帶更動其他團隊的作業。

04.01.02 建立與刪除的目的不同

Jira admin 或 space admin 可到 Space settings → Request management → Request types → Create request type，使用 Create blank 建立入口，設定名稱、說明、圖示、portal group 與適合的 work type，再儲存。目前 company-managed 官方文件把 Create from template 限定為 Jira admin；範本只是起點，建立後仍要檢查欄位及流程。S02

刪除是停用一個 request type 的結構，不是整理畫面用的捷徑。在該類型的 More actions → Delete request type 執行刪除前，先找出既有請求及任何使用它的管道。官方文件指出，有既有請求時會提示改用另一類型，原類型特有的顯示細節或欄位可能不再可見。電子郵件正在使用的 request type，還有先停用電子郵件請求的前提。S03 本課只在無正式資料的隔離練習環境示範刪除未使用的測試入口；正式移轉需要另外規劃。

04.01.03 與 04.01.04 portal groups 是導覽配置

到 Space settings → Channels & self service → Portal → Portal Groups，建立「借用設備」和「會議支援」兩組，在群組內使用 Add request form 加入既有 request type。相同 request type 可以放在不只一個群組，顧客從不同分類找到的仍是同一個入口。可拖曳群組與組內項目排序；文件指出，要有不只一個群組才會在 portal 顯示群組分類。S04

將某 request type 從所有 portal groups 移除，會把它藏出群組導覽。這不代表它變成機密入口：目前官方文件明說，這類入口仍會出現在搜尋中，也可加入 help center 的 topics。要測試「隱藏」，至少分開檢查群組瀏覽與搜尋；不要只看首頁消失就判定無法使用。S04

04.01.05 名稱、描述、圖示與 work category

名稱回答「我能在這裡做什麼」，描述回答「何時使用、要先準備什麼」，圖示協助辨認。將「AV-REQ」改成「借用會議設備」，比要求顧客認識內部分類更有幫助。修改名稱、說明後要儲存，並以 customer 身分檢查顯示。S05

工作類別（work category）則是 service requests、incidents、problems、changes、post-incident reviews 等 ITSM 作業分類，會帶來相應功能。一般借用適合 service request；「全棟會議影音突然失效」可能是 incident。分類選擇應符合處理目的及 work type 相容性，不能靠換圖示來取得事件管理能力。S06

要實際改分類，進到 Request types 的原工作類別，對目標 request type 選 More actions → Change work category，選新的類別後檢查 Continue／Confirm 的影響提示。原本 Unassigned 的類型可在目的類別用 Assign request types 加入。變更可能影響該類型既有與新工作項目的分類呈現；改成 Unassigned 也可能使該類別特有的欄位、細節或功能不再可見，所以應先在隔離副本驗證。S11

04.01.06、04.01.07 與 04.01.11 兩種畫面的欄位布局

進入某 request type 後，Request form 是客戶提交時填的內容；Work item view 是 agent 處理時的畫面。選擇對應分頁，從欄位面板加入欄位、移除不需要的欄位，再調整順序。這兩個視角必須分開驗證，不能把 agent 看得到當成 customer 一定看得到。S05

例如客戶表單依序詢問「一句話說明需求」「使用日期」「補充說明」，agent 畫面則保留 assignee、priority 等處理資訊。Display name 可以把 Summary 顯示成「一句話說明需求」；Display description 可以補上「例如：週三下午借一台投影機」。這是此入口的顧客文案，不是把底層欄位的身分改掉。S05

04.01.08 與 04.01.10 必填有不同層次

Field configuration（欄位配置）屬於 Jira 的底層設定，可決定使用該配置的工作項目是否允許某欄位留空。它通常需要 Jira admin 管理，並透過配置方案與 work type 對應；影響範圍可能跨多個 request types。官方也要求底層必填欄位應在 Create work item screen 可用。S07

Request form 的 Required 則是此顧客入口的要求。例如只在「借投影機」入口要求使用日期，與在共用 field configuration 把日期全域設成必填，是不同決策。前者不應被當成所有建立管道的共同驗證；後者可能讓其他入口、電子郵件或整合建立時缺資料。先問「哪種工作必須有？哪個管道能取得？」再選層次。

Screen（畫面）決定 Jira 的建立、編輯等畫面有哪些欄位；screen scheme（畫面配置方案）把不同操作接到相應 screen；work type screen scheme 再把 work type 對上適用方案。若 Request form 右側找不到欄位，請 Jira admin 核對欄位 context、field configuration 和相關 screen，而不是重複建立另一個同名欄位。共用 screen 加欄位可能影響其他使用者，且會出現在使用同一 work type 的 request types 的 work item view；各入口仍需檢查布局。S05S07

需要補入已存在的欄位時，目前官方的 Jira admin 路徑是 Space settings → Request management → Work types，選目標 work type，進 Fields，從 Select field 加入欄位。完成後回 request type 檢查是否可選、兩種畫面如何呈現，以及其他共用者是否受影響。這不是 space admin 在單一 request form 裡建立新全域欄位的替代方式。S12

04.01.09 預設值與隱藏欄位

Use preset value and hide from portal 會預填欄位並在顧客表單隱藏。例如設備借用一律先交給測試 agent，可在支援的欄位設定預設值；提交後再從內部工作項目確認值有寫入。這不是保密措施，也不是刪掉該欄位。S05

欄位支援有差異：Assignee 可作為預設且隱藏的欄位，不能直接讓客戶在 portal 表單選；Security level 則不屬於可加入 request type 的欄位。Summary 等必要系統欄位也不能因為想精簡表單而任意移除。遇到不能加、只能隱藏、或不能移除，要先辨識是哪一種限制。S08

04.01.12 顧客看得懂的狀態

在 request type 的 Workflow Statuses 分頁，可設定 Status name to show customer。例如團隊的「庫存檢查中」與「等待領用安排」都可對顧客顯示為「正在準備設備」。底層仍是兩個狀態，內部轉換並未消失；只是這段移動對顧客呈現同一名稱。測試時同時查看 portal 與工作項目歷程，避免用顧客名稱推斷 SLA 或 automation 的底層狀態。S09

04.01.13 真正控制誰可以提出這種請求

若只有設備管理團隊能提出「報廢設備」，應使用 request type 的 Restrictions，加入獲准的使用者、群組、客戶帳號或組織，再套用。未列入允許範圍的人連搜尋都不會看到可用入口；管理員或 agent 身分不代表自動例外。這個限制控制建立請求，不控制請求建立後誰可閱讀；後者要另外檢查分享與 work item security。S10

目前官方限制還包括：受限制的 request type 不能供 email、chat、widget 或 virtual agent 使用；automation 或 app 身分也要檢查是否獲准。因此「把所有入口都鎖起來」可能直接破壞原本的接件管道。安全的做法是先列出使用者與管道，再挑一個專用入口進行限制測試。S10

隔離練習 從借用需求走到可觀察結果

前提：使用管理員事先批准的隔離 company-managed 測試專案；準備兩個虛構客戶身分「練習客戶 A、B」及一位測試 agent。不得使用真實客戶、正式收件匣或共用 production workflow。需要 Jira admin 的步驟先由該管理員準備，沒有權限就記錄待確認，不繞過權限。

  1. 記錄目前「設備借用」示範 work type 使用的 workflow、screens 與已有欄位。確認它未與正式專案共用。使用者介面中的實際名稱若不同，以當地標籤記錄，不新增多餘類型。
  2. 建立「練習：借投影機」及「練習：借麥克風」，使用相同 work type。預期兩者名稱不同，但底層 workflow 相同。
  3. 建立「借用設備」與「會議支援」兩個 portal groups，將投影機入口加入兩組。以客戶 A 瀏覽；預期不同導覽位置都開到同一類型。
  4. 在投影機 Request form 調整 Summary 顯示名稱與說明；只把已由管理員提供的日期欄位設為此表單必填。預覽留空與完整填寫的結果。
  5. 若該隔離環境允許，為 Assignee 設定測試 agent 預設值並隱藏。提交一張全為虛構內容的請求；比對客戶表單、提交後 portal 與 agent 畫面三者差異。
  6. 將投影機入口移出所有 portal groups。記錄群組導覽消失，接著搜尋它。此步觀察的是導覽，不是權限。
  7. 將入口加回群組，再於 Restrictions 僅允許客戶 A。用 A、B 分別檢查入口與提交能力；既有工單閱讀則另測，不混為同一驗證。
  8. 將兩個內部示範狀態映射成同一顧客名稱，由測試 agent 移動測試工單，並比較內部歷程與顧客畫面。
  9. 只對另一個完全未使用的「練習：待刪入口」演示刪除。若看到影響既有請求的提示，停止，先記錄影響與移轉需求。

本課沒有執行上述操作；每個「預期」都應在獲准的實際測試租戶重新驗證。UI rollout、權限及共用配置會影響可見選項。

查看答案與理由
  1. 改該 request type 的顧客文案；不需要為此更動共用 work type 或 workflow。
  2. 不能。群組移除只影響導覽；要限制建立應檢查 Restrictions，閱讀既有工單又是另一層。
  3. 檢查 field configuration、管道的 request type 與是否有安全有效的資料來源；不能只把客戶欄位藏起來當作解決。

摘要

先辨識 request type、work type、workflow 與 screen 的責任，再設定客戶欄位及 agent 布局。Portal groups 幫顧客找入口；Restrictions 控制誰能提出該類型請求；既有工單閱讀權限另行管理。

常見陷阱

  • 把「藏出 portal groups」當成安全限制
  • 為單一表單需求修改共用 field configuration，卻沒有檢查其他管道
  • 誤認顧客狀態別名會改變底層 workflow
  • 為 email 或 virtual agent 使用的類型加入不相容的 Restrictions

觀念釐清

顧客的 Request form、提交後 portal 詳細資料、agent 的 Work item view 是三個不同觀察位置。欄位出現在其中一處，不足以推論另外兩處的可見性或編輯能力。
