02.02 Configure SLAs 設定服務等級協議

適用範圍：Jira Service Management Cloud。主操作示範採 company-managed service project；team-managed 的按鈕差異另列。本課是原創教學與練習，並非 Atlassian 官方試題，也不宣稱題目命中率、單元考試配分或考試作答時間。

考綱依據：ACP-420 V2 April 2025，第 2 頁。本課完整涵蓋四項要求：說明 SLA 用途、把團隊與客戶需求轉成設定、設定條件／目標／行事曆，以及疑難排解。

用語對照：考綱的 project（專案）對應部分新介面的 space；issue 對應 work item（工作項目）。2026-10-05 的部分官方 Cloud 文件已使用這些新詞。本課正文使用「專案／工作項目」，操作路徑保留文件中的英文選單，方便新舊介面對照。以下路徑經公開官方文件核對，未登入使用者的 Jira 站台實測。建立與編輯 SLA

零基礎先備：先懂欄位，才看得懂碼表

JSM 的工作項目記錄一次服務請求。Status（狀態）描述目前進度，例如處理中；Resolution（解決結果）記錄結案的結果，兩者不是相同欄位。Workflow（工作流程）定義狀態及允許的轉換；若轉到完成狀態時沒有設定 Resolution，採用 Resolution: Set 作為完成事件的 SLA 不一定會結束。

Metric（指標）是你要量的事情，例如首次回覆；goal（目標）是某群請求允許多久及採哪個行事曆；cycle（週期）是一次開始到完成的量測。Elapsed 是已計入的時間，remaining 是相對目標尚有的時間，breach 是超過目標。SLA 不會替你修好問題，也不會因為在畫面變紅就自動加派人手；它提供可用來排工作或觸發另設規則的訊號。

本課將採一張固定設定的請求逐段算時間。先讀懂「哪些分鐘符合計入條件」，再看畫面色彩，才能分辨是承諾不同、日曆不同，還是流程設定錯誤。SLA 指標 · 條件

SLA 的目的與設定主線

你要解決的問題是：「哪些客戶請求，需要在什麼服務時段內，完成哪件事？」

SLA 把服務承諾變成可追蹤的時間目標，協助 agent 判斷處理順序。首次回覆和解決問題是不同衡量指標；回覆過客戶，不代表已完成修復。SLA 用途

設定時先回答五個問題：

  1. 誰適用：哪些工作項目符合目標的 JQL？
  2. 何時開始：哪個事件啟動計時週期？
  3. 何時不計：是否符合暫停條件，或處於行事曆外？
  4. 何時完成：哪個事件結束週期？
  5. 允許多久：此目標的時間上限與服務行事曆是什麼？

「等待客戶」是你設定的暫停條件；「星期日不營業」是行事曆規則。兩者都可能讓經過時間不再增加，但診斷原因不同。官方 JQL 的 paused() 指條件暫停；withinCalendarHours() 判斷行事曆時段。SLA JQL 說明

速記：先圈對象，再找起訖事件，接著排除不計時區間，最後比較目標。

觀念釐清

把一個 SLA 想成「帶規則的碼表」：

  • 條件決定週期邊界與暫停狀態
  • 目標用 JQL 選擇適用工作項目，並指定時間上限與行事曆
  • 行事曆提供時區、工作日、服務時段與假日

在本課的固定目標案例中，累計時間就是：啟動後、結束前，同時位於工作時段且未符合暫停條件的時間總和。這是依官方條件與行事曆規則整理的教學模型；同一分鐘即使同時是午休和等待客戶，也只排除一次。條件 · 目標 · 行事曆

兩個容易混淆的邏輯

同一組開始條件列了多個事件，符合其中一個便可觸發；完成條件亦以任一符合為準。不要把畫面上分開列出的條件誤讀成必須全部成立。條件規則

多個 SLA 目標則由上往下比對，採第一個符合的項目。把很寬鬆的 JQL 放前面，可能遮住較下面的特殊服務目標。Cloud 疑難排解

把需求翻成設定

以下數字、標籤、工作流程與團隊名稱均為本課自行設計的案例；練習專案代碼假設為 SUPPORT。

需求：台灣支援團隊平日 09:00–12:00、13:00–17:00 服務；一般請求 4 個服務小時內回覆、8 個服務小時內解決。標籤 vip 的請求需 1 小時內回覆、3 小時內解決。處理解決問題期間，可以扣除等待客戶補件的時間。

這些決策依目標的 JQL／Calendar 設定、公開留言與解決欄位事件、以及可選的 Pause 規則組合而成。設定目標 · 事件選項 · 條件

首次回覆 SLA 的本案例設計：Start 為建立請求，Finish 為對客戶的公開回覆；不加等待客戶暫停。解決時間 SLA 的設計：建立請求開始，等待客戶時暫停，設定 Resolution 時完成。這些是案例選擇，不能當成每個站台必然相同的預設值。

需求若改成「所有狀態都算在三小時內」，就不要自行加入等待客戶暫停；若寫「三個實際小時、全年無休」，則應採符合 24×7 服務的行事曆。先忠實反映承諾，再考慮設定便利性。

操作前的權限與方案檢查

  • 建立／修改 SLA：官方說明要求 project admin 或 Jira admin；team-managed 文件也要求 admin。一般 agent 可查看 SLA，不應直接推定有設定權限。依優先順序分組目標 · team-managed 設定 · 角色
  • 本課使用 JSM 原生 SLA。官方 Free 方案介紹也將 SLA Management 列為功能，並列出最多 3 位 agents；因此基本 SLA 管理不是 Premium 專屬。其他進階功能仍應個別查方案，不能從基本 SLA 推論全部功能都免費。官方 Free 方案 · 目前 Service Collection 方案
  • 可明確核對的方案差異：在客戶入口顯示 support timeline 屬 Premium／Enterprise。這是顯示功能的限制，不應拿來推論所有 SLA 計時功能都需要 Premium。入口時間目標
  • Atlassian 雲端服務的 uptime SLA 與專案內的回覆／解決時間 SLA 是不同承諾。不要把價格頁上的可用率保證當成本課的計時器設定。服務方案說明

A 建立服務行事曆

  1. 在服務專案進入 Space settings → Request management → SLAs
  2. 點 SLA 頁面右上角的行事曆圖示，選 Add calendar
  3. 輸入名稱，例如 TW support；時區選 Asia/Taipei
  4. 勾選週一到週五；每日加入 09:00–12:00 與 13:00–17:00 兩段
  5. 依實際服務承諾登錄假日，儲存

建立完行事曆，仍要在適用的 SLA goal 指定它。不要只建立日曆就以為所有目標會自動改用它。官方行事曆步驟 · 指定目標行事曆

B 建立指標與目標

  1. 回到相同的 SLAs 頁面，選 Add SLA
  2. 命名為可辨認用途的指標，例如 Support resolution time。官方提醒：建立後不能直接改 SLA 名稱
  3. 在 Goals 選 Add goal；於 Apply to work items 輸入 project = SUPPORT AND labels = vip，Time target 設 3h，Calendar 選 TW support
  4. 加入一般目標 project = SUPPORT，Time target 設 8h，並選同一行事曆；將它放在 VIP 目標之後。此處 SUPPORT 是假設的練習專案代碼，實作時替換為自己的專案代碼
  5. 設定下一節的 Conditions，最後 Save

命名與設定完成後，先用 VIP／一般請求各驗證一次。建立 SLA · 設定目標 · 目標順序

C 設定週期條件

在 SLA 設定頁面找到 Conditions；若是修改現有指標，先在 SLAs 清單選該指標的 Edit：

  • Start 區加入工作項目建立事件
  • Pause 區加入「狀態為等待客戶」的條件；請挑選此站台實際使用的狀態
  • Finish 區加入設定 Resolution 的事件
  • 儲存後以測試請求驗證實際歷程

介面區段的官方名稱為 Start counting time when、Pause counting time when、Finish counting time when；事件下拉項目可見 Issue Created、Resolution: Set 等舊用語。狀態名稱取決於站台工作流程，不應假定全站都叫 Waiting for customer。條件操作 · 事件選項

D 介面差異與可擴充設定

team-managed 官方步驟使用 +New Metric 建立，結尾為 Create；編輯時為 Save。其 Goals 欄位列為 Work items (JQL)、Goal、Calendar。不要因為看不到 Add SLA 就判定此專案不能用 SLA。team-managed 版本

若多組目標只是優先順序不同，可在同一父層 JQL 下用 Add priority 加入各 priority 的時間與行事曆。這些 priority 與父層條件一起成立；All remaining priorities 是該群組內最後比對的後備值。優先順序分組

建議驗收至少覆蓋：一般／VIP 各一張、營業內／外建立、進出等待客戶、解決事件、假日，以及多個目標皆符合的情形。這是本課的測試建議，不是官方宣告的固定驗收清單。

案例設定

以下為原創固定規則情境：

  • Calendar：Asia/Taipei，週一至週五 09:00–12:00、13:00–17:00，案例期間沒有假日
  • Goal：3h；整個案例不變更優先順序或目標
  • Start：星期五 16:00 建立請求
  • Pause：星期五 16:30 進入等待客戶
  • Resume：星期一 12:45 已離開等待客戶狀態，暫停條件不再成立
  • Finish：星期一 15:00 設定 Resolution

變更後的兩個陷阱

  1. 進行中的請求改了 priority，已累計時間會算進新目標，不會只因 priority 改變就歸零。例如已用 1h20m、改成 2h 目標，在其他規則不變時只剩 40m。
  2. 一般編輯 SLA 不會重新改寫已完成的週期。開始／完成條件的修改可能影響進行中的週期；不要保證所有歷史請求都會以新規則重算。編輯行為

進階排錯延伸（本目標不要求新手實際執行破壞性重建）：官方另有單筆重新計算與破壞性重建的排查方式。先核對設定與歷程，再由有權限的管理員處理。破壞性重建可能刪除原 SLA 歷史，按目前目標重新計算，甚至把原本達標的紀錄變成逾時；不要把它當一般「重新整理」。文件要求執行重建者同時有 Jira Administrator 權限及目標專案的 Agent 身分。重建風險與權限

時間看起來相差數小時，也要核對時區：SLA 依行事曆時區計算，tooltip 顯示可依個人 Jira 時區設定呈現。SLA 顯示與時區

常見陷阱

  • 「4h 就是建立後四個實際小時」：只有服務時段與條件真的允許持續計入時，兩者才相同
  • 「沒跑就是 Pause condition 成立」：也可能只是行事曆外
  • 「符合兩個 goal 就採最嚴格的那個」：要先看順序，不是比較哪個數字最小
  • 「Done 一定滿足 Resolution: Set」：需要查欄位與事件
  • 「客戶回覆必然解除等待」：若工作流程沒變，暫停條件仍可能成立
  • 「優先順序升高就從零開始」：既有累計時間會計入新目標

規則來源分別見前面的心智模型、疑難排解與變更行為；這些句子是教學歸納，不是官方試題原文。

隔離實作：建立一個看得見結果的 SLA

只在核准的獨立教學專案執行。準備 space admin、獨立 customer 與 agent 測試帳號，沒有真實個資或正式通知。不要讓同一帳號同時當 reporter 與 assignee，避免角色重疊影響條件判讀。先記錄原有 SLA，不更動共用正式配置。建立 SLA 的角色提醒

  1. 依前面的步驟建立教學行事曆，再建立一個明確命名的解決時間 SLA；將日曆指定到 goal。只建立日曆而沒選入 goal，不算完成
  2. 設 Start 為建立請求、Pause 為教學 Waiting for customer 狀態、Finish 為 Resolution: Set。先請管理員確認教學 workflow 的解決與重開轉換會分別設定／清除 Resolution
  3. Customer 建立一張不帶 VIP 的請求，再建立一張帶 VIP 的請求。以 agent 查看各自採用的目標；核對更上方的目標是否先匹配
  4. 將其中一張轉入 Waiting for customer，記錄時間與 elapsed；用一次公開回覆和一次內部留言分開驗證，觀察它們不一定改變同一件事。若 workflow 不會因回覆離開等待狀態，應看到 Pause 持續
  5. 讓 agent 將請求解決，核對 Resolution 真正有值以及 SLA cycle 完成。只看到 Done 字樣不足以判斷
  6. 若教學流程允許重新開啟，清除 Resolution 並驗證符合已配置的 Start 時可形成新週期；保留前一輪結果，不做破壞性重建
  7. 用本課週五到週一的事件表做紙上計算，與當前可在實驗中觀察的短時間測試分開記錄。不能把沒經歷的三天時間線寫成實機測試結果

完成證據應包括設定的 goal、calendar、conditions，以及至少一張實際測試單的欄位／狀態歷程與 SLA 結果。本課提供操作與期望，並未替任何人執行這些變更。

查看答案與理由
  1. 兩者要衡量的完成事件及時間承諾不同。2. 不計，暫停條件解除不會取消行事曆限制。3. 剩 40 分鐘，已累計時間不因單純改優先順序歸零。4. 不會；一般編輯保留已完成週期，破壞性重建則是風險不同的管理操作。

重點回顧

先說清楚適用對象、起點、停點、排除時段及時間目標，再做設定。驗證時，用工作項目歷程和行事曆逐段計算，並確認採到第一個符合的 goal。不要只看碼表顏色、狀態名稱或設定頁有沒有按儲存。
