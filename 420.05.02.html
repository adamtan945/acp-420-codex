05.02 Virtual service agent 與知識庫回答

假設服務團隊每天都收到「會議室螢幕沒有畫面」的問題。有些人只要看一份接線說明就能解決；有些人需要一步一步排查；也有人真的需要服務人員到現場。Virtual service agent 的設計是把這幾條路徑接起來，而不是一律產生一段看似流暢的回答。

名詞與目前產品前提

考綱稱 Virtual Agent；目前 JSM 文件稱 virtual service agent（虛擬服務代理）。Intent（意圖）代表一種特定問題或需求；training phrase（訓練語句）是顧客可能怎麼提出它；conversation flow（對話流程）是辨識後逐步怎麼協助；AI answers 會從連結的知識庫找內容並產生回答。Escalation（轉交真人）在這裡會建立工作項目，讓 agent 接手。

目前文件的建立入口是 Studio → Agents → Create an agent → Virtual service agent。前提包含 Service Collection Premium 或 Enterprise、organization admin 已啟用 AI，以及操作者為 space admin。文件也列出 Atlassian Government 環境不提供此功能。這些是 2026-10-05 查核到的產品條件，不能用「所有 JSM 都可開啟」概括。S01

Virtual service agent 與可顯示在 portal 的一般 Rovo agent 是不同選項；帳號適用性與功能也不應直接互換。ACP-420 此課聚焦 intents、標準流程、預設 request type、AI answers 與對話分析，不把任意 Rovo agent 設定當成同一考點。S01

安全前提：只在已批准的隔離環境使用虛構內容測試。啟用 intent 或 AI answers 可能立即讓連接管道提供服務；不是只有按下「建立」才會影響真實顧客。沒有上線授權時停留在測試，不能為了練習啟用正式服務。S01S07

05.02.01 Default request type 決定接手案件的基本入口

Virtual service agent 需要建立請求時，通常使用它的 default request type（預設請求類型）；個別 intent 的 conversation flow 可透過 change request type and fields 步驟覆蓋。這個預設是讓不屬於特定流程的求助仍有清楚的落點，不是把所有 intents 都當成同一件事。S02

目前路徑為服務專案 Space settings → Channels & self service → Virtual service agent → Manage in Studio → Identity，展開 Jira Service Management settings，選 Default request type 並儲存。應挑一個對顧客清楚、可在 portal 使用、且不要求代理無法填出的資料的入口。S02

官方該頁明列「不隱藏於 portal」及「沒有 required fields」兩項條件。理解上要特別檢查額外的必填資料會不會阻止代理建立請求；不要因此任意移除 Jira 必要系統欄位。官方 request form 文件另指出 Summary 等必要系統欄位不能移除，實際相容性須在隔離租戶驗證。也不要挑使用 Restrictions 的入口，目前它不支援 virtual agent 管道。S02S03

若自動建立失敗，代理可能提供此入口的 portal 連結讓顧客求助。因此預設入口的可見性與可填寫性是故障時的備援，不只影響正常分類。

05.02.02 以問題為單位建立 intent

一個好的 intent 可以用一句話說清楚：「協助處理會議室螢幕無畫面」。太廣的「所有設備問題」會混進許多不同流程；太窄的「某條線插在某孔時畫面閃一次」又難以維護。這是教材的設計建議，判斷標準是顧客是否會以相近語意求助，以及是否有相同處理路徑。

從 Manage in Studio → Intents → Add intent，可選範本或 Start from scratch，填內部名稱、描述與客戶會看到的 Display name，再加入 training phrases。現在建立步驟要求三句起始語句；本案例可以自寫「The meeting room screen is blank」「I cannot display my laptop in the room」「The room monitor shows no picture」。語句教系統辨識問題，不是給顧客看的逐步答案。S04S05

接著設計 conversation flow：先問是否已選對輸入來源，提供安全的接線檢查說明，再問是否恢復。若未恢復，收集房間名稱等非敏感資料並轉交真人。不要要求使用者輸入密碼或自行執行高風險管理操作。流程與訓練語句要分開調整：認錯問題時改辨識資料；認對問題卻無法協助時改流程或知識內容。

儲存 intent 不等於已驗證。先用沒有出現在 training phrases 中的新說法測試，例如「投影有訊號但顯示器黑的」。還要以相似但不同需求測試，例如「我想預約一台螢幕」，看是否錯誤命中。正式啟用前確認 fallback 與真人接手路徑。

05.02.03 標準流程管理共通對話

Standard flows（標準流程）處理各 intents 共用的開場、辨識、解決或轉交。從 Manage in Studio → General 展開相應流程，編輯文案後儲存。它與某一 intent 的完整解題流程不同。S06

  • Greet：說明現在由虛擬服務代理協助。文字要短，避免假裝是真人。官方允許把 Message 留空來關閉此招呼，不代表整個代理停用。
  • Match intent：根據信心程度確認意圖、提供可能選項、嘗試 AI answers 或請顧客重新說明。文案要幫助顧客修正誤解，而非暗示已經確定找到答案。
  • Escalate：告知已代為建立請求並轉給真人。訊息不要承諾未被服務流程支持的到場或回覆時間。
  • Resolve：考綱用語如此；目前文件呈現 Resolve with CSAT，在確認解決後收集 customer satisfaction（顧客滿意度）。「回答過」與「顧客確認已解決」不同。
  • Auto-close：處理暫停互動的對話。是否記為 resolved 或 closed 也取決於先前有無意圖命中／AI 回答，以及顧客回應，不能解讀成所有無回應都是成功解決。S06S08

目前另有 Offer options，可讓顧客選擇提出請求、看搜尋結果或改問法，這是對考綱標準流程的現行介面補充。它的詳細選項屬版本相關內容，教學應保留標示，不能把新增選單名稱反過來刪除考綱的核心概念。S06S08

05.02.04 用 AI answers 前先確保知識可用

AI answers 適合能以資訊或操作說明解決、且知識庫已有正確內容的問題。它會搜尋連結的 knowledge base spaces 並整理回答；不必為每個文章題目都建立 intent。當功能啟用，第一則訊息仍先嘗試高信心的 intent，未命中時才嘗試 AI answers。S07

啟用前由管理員確認 AI／Rovo 可用、服務專案已連結知識庫、官方要求的 Who can view 設定，以及 Confluence indexing language 與文章語言相符。當前啟用文件要求連結知識庫的 Who can view 為 All logged-in users；不能在有敏感資料的正式 space 上為此任意放寬權限。應先提供合適的、已審核的示範知識庫。S07

操作入口為 Manage in Studio → Knowledge，在 AI answers 開關後選 Activate。文件指出會立即在已連接管道生效，所以要先使用測試功能檢查，再取得上線批准。文章使用會反映顧客的知識庫權限；Slack 另有只使用 All logged-in users 文章的限制，不能把 portal 測試結果直接套到所有管道。S07

文章品質仍是管理工作：過時的接線方式會讓回答看似完整卻無用；只有標題沒有解法，代理也無法憑空知道公司設備。優先修正來源文章，再測相同問題與相鄰問題，不靠增加一段誇張的招呼文字改善正確率。

05.02.05 對話紀錄告訴你該改哪裡

到 Manage in Studio → Conversations，選時間區間並使用 filters。Action 的 Matched、AI answered、Unassisted 說明協助方式；Resolution 的 Escalated、Resolved、Closed 說明結果。這是兩個維度：AI answered 仍可能 Escalated，Matched 也可能讓顧客最後需要真人。S09

原創分析例子：十段「螢幕無畫面」對話有八段命中正確 intent，但六段最後轉真人。你不能只看到八段命中就宣布服務成效好。應讀取有權查看的對話：是否流程漏問訊號來源？是否文章示範不同型號？是否本來就需要現場更換設備？最後一種轉真人可能正確，不應為了壓低數字讓顧客卡在循環。

若大量 Unassisted，檢查缺少的需求與 training phrases；若 AI answered 後常轉真人或低 CSAT，檢查引用文章是否缺漏或過時；若辨識對但途中無法完成，檢查 conversation flow。當前文件說 Conversations 頁只含 portal、help center 與 Slack 的資料，並非所有管道都能查看完整對話。統計前先了解資料範圍，不能把缺資料當零件數。S09

隔離練習 一段可接手的設備協助對話

前提：有適用方案、已獲准的 AI 使用及隔離測試 portal；知識庫只含虛構設備說明。沒有符合前提的租戶，改以本課紙上案例練習，不購買方案、不更改正式 AI 或權限設定。

  1. 檢查 Studio 中建立的是 Virtual service agent。記錄方案、管理角色與測試管道，避免誤用一般 Rovo agent。
  2. 指定「練習：需要人工協助」為 default request type，檢查 portal 可用性及不相容必填欄位，預先走一次人工接手的建立測試。
  3. 建立「螢幕無畫面」intent，加入三種原創說法，設計兩個安全檢查步驟及解決／轉真人兩個出口。
  4. 在測試模式送入正確需求、相似但不同需求與完全無關問題。記錄辨識與流程結果，不只看回覆文字。
  5. 修改 Greet、Escalate、Resolve、Match intent 與 Auto-close 的可編輯文字；逐項確認沒有錯誤承諾。
  6. 用已連結的公開示範知識測試 AI answers。只有環境負責人批准上線時才 Activate，因為這可能即時影響所有連接管道。
  7. 若產生可用測試對話紀錄，以 Action 與 Resolution 交叉檢查，挑一段成功、一段轉真人、一段無協助案例閱讀，寫出各自該改善什麼或為何無須改善。

驗證限制：未在租戶執行。特別需要補測 default request type 必填相容性、各管道呈現、Conversations 可用範圍，以及方案／Studio rollout；不以文件核對冒稱對話已成功。

  2. 不能，處理方式與結果是不同維度。
  3. 不是，官方文件指出啟用會立即影響連接管道，須先測試並取得相應上線授權。

摘要

Virtual service agent 結合意圖辨識、對話流程、知識回答與真人接手。先確認方案、AI 與知識庫前提，再驗證預設 request type；最後用對話方式與結果一起評估成效。

常見陷阱

  • 將 virtual service agent 等同任何 Rovo agent
  • 預設入口藏起來或有代理無法取得的必填資料
  • 用訓練語句代替解題流程，或將意圖命中率當解決率
  • 為啟用 AI 任意放寬正式文章權限
  • 在不知道會立即生效的情況下啟用 intent 或 AI answers

觀念釐清

Automation flow、conversation flow 與 Jira workflow 都有「流程」一詞，但分別用來自動執行規則、引導對話、管理工作狀態。它們會互相連接，不是同一個編輯器或同一套設定。
