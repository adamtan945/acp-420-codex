事件通知與共用文字不是同一機制

客戶通知由事件、啟用狀態與收件人配置決定，共用回覆則由 agent 選入編輯器後再送出。排查重複或沒有收到時，要分別核對原生客戶通知、內部通知與自動化，不把所有信件視為同一來源。

用一個例子理解

測試 customer A 提出假單，珊使用 Shared canned response 填入「LAB420 已收到」。插入文字時尚未對外送信；真正按公開回覆後，A 的 portal 可看到內容，通知是否到專用收件匣另作一項證據。

05.03 通知與共用回覆

服務團隊需要讓顧客知道案件有進展，也需要在內部討論處理方式。這兩種訊息不能混在一起。

本課先教你分辨 customer notifications（客戶通知）與 internal notifications（內部通知），再配置通知事件、內容與 canned responses（預存回覆），最後用有證據的方式查明為什麼有人沒收到。

名詞與前提

Event（事件）是系統中發生的動作，例如公開留言新增；recipient（收件者）是符合通知規則的人；template（範本）提供通知格式；variable（變數）會在寄出時帶入工單資料。

Reporter 是提出請求的人，request participant 是被加入一起參與請求的人，watcher 是內部追蹤工作的人，這些角色不應互相替代。

Work item（工作項目，考綱稱 issue）可能同時有 Reply to customer（公開回覆）與 Add internal note（內部註記）。Public 的意思是對有該請求存取權的客戶可見，不代表在公開網路上任何人都看得到。本文以 company-managed 服務專案為主；

目前介面使用 service space／Space settings。編輯客戶通知與建立 Shared 預存回覆需要 space admin，內部 notification scheme 的維護可能需要 Jira admin。S01S02S05

05.03.01 先確認是哪一種事件

通知的設計先從「顧客需要知道什麼」開始，再找相符事件。常見事件如下，各自有不同觸發意義：S03

  • Customer invited：客戶受邀使用服務入口
  • Request created：請求建立後的收件確認
  • Public comment added／edited：顧客可見留言新增或修改
  • Request resolved：Resolution 欄位被設定，並非只是狀態名稱剛好叫 Done
  • Request reopened：Resolution 被清除
  • Participant added：加入請求參與者
  • Organization added：請求分享給組織
  • Approval required：進到需要核准的階段
  • Customer-visible status changed：顧客看得到的狀態改變

例如內部從「工程調查」移到「廠商協調」，若都映射為同一顧客狀態，不能只憑內部狀態有變就預期顧客看見不同狀態。要查實際發生的事件及通知條件。新增 internal note 也不應當成 Public comment added 來期待客戶收到內容。

05.03.02 每個事件可分別啟用或停用

在 Space settings → Notifications → Customer notifications 選通知事件，進入 Edit，可檢查 To（收件者）、內容以及 Enable 開關，儲存後生效。停用一項事件不等於停用所有通知，也不會停止接收 email requests。S02

比如設備借用服務保留 Request created、Public comment added 與需要採取行動的通知，但不希望每次細小變化都打擾客戶。先在測試專案只關閉要評估的事件，再以兩筆不同測試記錄比較。不要一次關閉全部後，靠印象猜是哪項造成客戶漏訊息。

「事件開著」只是條件之一。還要看該通知選了哪些人、是否排除觸發動作的人、客戶在此請求是否開啟訂閱，以及是否具備正確身分。某些通知或收件者類別有特殊行為，例如需要核准或請求解決時不一定跟一般訂閱通知完全相同。因此不能用一句「取消訂閱就不會再收到任何信」包辦所有事件。S01S02

05.03.03 主旨與正文分開處理

顧客通知的共用主旨／樣式在 Customer notifications → Templates → Edit templates 設定；各事件的正文則在該事件的 Edit 中調整。修改主旨時保留 work item key，有助同一請求的通知維持同一郵件對話。

不要為了主旨好看，把案件識別資訊全部移掉。S04

原創正文示例可以是：「您的設備申請有新進度。請從請求連結查看最新回覆。」實作時由 Insert variable 選單插入該事件支援的 Request URL、Request status、Work item key 等，不手打猜測變數。

這些通知變數的格式不是 automation smart values 的任意同義寫法；UI 改叫 work item 也不代表所有變數中的 issue 字樣要手動改掉。S02

不要把內部分析、憑證或與此顧客無關的資料放入顧客通知。若站點啟用 safe customer notifications，摘要、描述或留言資料可能在信中遮蔽；應讓文字清楚引導客戶登入 portal 看內容，不把遮蔽誤判成變數壞掉。這項安全設定由站點管理決定，本課不指示停用。S02S06

完成後，使用預覽與獲准的測試收件匣檢查主旨、正文、變數、連結、語言及回信串接。翻譯需到 Language support 維護；改一種語言的 email template 不會保證其他語言自動跟著更新。

05.03.04 客戶與內部通知是不同路徑

某條路徑停用，不代表其他路徑也停止。

Customer notifications 是提供給請求中相關客戶角色的服務更新。Agent 或 admin 若在某張請求是 reporter 等客戶角色，也可能依客戶路徑收到通知；不能僅憑職稱判定。

Internal notifications 則由 Jira 的 notification scheme 驅動，面向符合內部資格與事件收件者的 agent／admin，包含 assignee、watcher 等情境。S01

Notification scheme（通知配置方案）把 Jira 事件對應到收件對象；它不等於前述 Customer notifications 清單。某人同時兼具 agent 與此單客戶角色時，內部通知有優先的互動規則，可能改變他收到哪一路訊息。

因此「我自己是管理員，我沒收到客戶信」不是有效的單一測試。使用獨立的純 customer 測試帳號更容易釐清。

內部 note 用來寫「正在請廠商確認零件」，公開 reply 用來寫「我們正確認可用設備，稍後回覆」。選擇 canned response 或通知文字前，先確認編輯框是 internal note 還是 reply to customer；一致的用語不會自動保護錯誤的可見性設定。

有順序地排查沒有收到或收到兩次

  1. 確認期待的事件真的發生，例如是公開留言，還是 internal note；是 Resolution 被設定，還是只有狀態名稱改變。
  2. 判斷收件者在該請求扮演什麼角色，核對應走 customer 還是 internal 路徑。
  3. 檢查事件 Enable、To、排除觸發者與訂閱偏好，再看存取權限。
  4. 查 Email logs 的客戶通知失敗紀錄；目前官方文件說成功寄送紀錄不保存，因此「沒有失敗 log」不能當成對方一定收到的證據。

  5. 再檢查對方的垃圾信／信箱過濾。若重複收到，對照發送來源，看是否同時有額外 automation、不同事件或其他系統寄信；先找證據，不先全部停用。S01S07

目前 Email logs 是整合寄出客戶通知與寄入處理的入口，取代舊 Customer notification logs 入口。Processing log 對應寄入信如何處理，Connectivity log 對應自訂信箱連線；不要在錯誤分頁找同一種證據。S07

05.03.05 Shared canned responses 讓團隊共用可靠文字

預存回覆讓 agent 手動插入常用文字，再依案件調整。它不是事件通知，也不會因為儲存就自動寄信。例子是「請提供螢幕上顯示的錯誤訊息，並移除畫面中的個人資料」；每次使用仍要檢查對象與情境。

Space admin 在一張測試工作項目開啟 Add internal note 或 Reply to customer，選 Canned responses → Create new，設定容易搜尋的 Name、Availability 與 Response。

選 Shared 可讓服務專案 agents 共用；Personal 只供本人使用。官方目前說 agent 只能建立 Personal，且建立後不能直接改 availability。S05

因此不要先建立一堆 Personal 再假設可一鍵轉 Shared。先決定用途與權限，再建合適範本。可加入支援的變數，例如工作項目 key 或 reporter 名稱；插入後檢查實際展開值與公開／內部模式，再決定是否送出。共用文字應避免承諾未經同意的退款、時程或服務保證。

隔離練習 通知對照實驗

前提：隔離服務專案，只有受控測試信箱與虛構人物。客戶通知與公開回覆可能真的發信，所以測試收件者必須已獲授權；沒有則只做配置預覽，不能把真實客戶當測試對象。

  1. 建立一張由純 customer 測試帳號提出的虛構設備請求。記下 reporter、participants、assignee 與 watchers。
  2. 確認 Request created 與 Public comment added 的事件設定與收件者，保留原始配置以便復原。
  3. 由測試 agent 分別新增一則 Internal note 與一則公開回覆，觀察 portal、客戶信箱與內部信箱，將三種證據分開記錄。
  4. 修改測試通知正文與主旨，保留 key 與請求連結。先預覽，再用允許的測試收件匣收取，檢查變數與語言。
  5. 只停用一個非必要測試事件，重新觸發並比較；再復原。若不符合預期，按照事件、角色、啟用、收件、log 的順序查。
  6. 由 space admin 建立一個 Shared 預存回覆，以另一個測試 agent 插入而不立即送出；確認它可共用、可編輯，而且不會自行發送。
  7. 比較一位兼 reporter 與 assignee 的測試 agent 和純 customer 的通知，記錄角色混合帶來的差異，不把某一封缺信直接當全系統故障。

驗證狀態：上述操作未在租戶執行。方案限制、UI rollout、safe customer notifications、郵件供應者政策都可能影響可見結果，需以真實測試證據補上。

摘要

先分辨事件、收件角色與通知路徑，再修改內容或追查寄送。Shared canned responses 協助人工回覆的一致性；它與自動通知分屬不同機制。

常見陷阱

  • 以管理員自己的收信情形代替純 customer 測試
  • 將內部 note、公開 reply 與所有人的網路公開混淆
  • 把狀態名稱 Done 當成 Resolution 必然已設定
  • 為美觀移除主旨的 work item key，或亂改變數語法
  • 把沒有失敗 log 當投遞成功證明

觀念釐清

收到通知取決於事件、啟用狀態、角色、收件設定、訂閱與投遞。只有「有發生更新」不足以推論每個參與者都應收到同一封信。
