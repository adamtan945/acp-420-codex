常見陷阱

從零開始 先看懂Jira Service Management

把顧客當agent、把request type當work type、把queue當工單儲存資料夾、把所有管理員當同一種角色、把Data Center文章套用Cloud、為跟課而操作production。

01.01 身分、角色與多層權限

  • 收到通知或成為 watcher，不等於取得案件的查看權
  • Customer organization 不是 Atlassian 管理組織，也不是授權用 group
  • 有 Jira 授權並不自動等於 JSM agent；Service Desk Team 成員資格也不會單獨創造產品授權

01.02 客戶、組織與請求分享

  • Restricted 不等於已封鎖 chat 管道
  • 免登入提交不等於匿名查看私人請求
  • 修改 detail field 的名稱／類型設計，和修改某個人的資料值，影響範圍不同

01.03 服務團隊、指派與存取排錯

  • 專案角色名單的 Remove 不代表刪除帳號，也未必移除群組繼承權
  • Project lead 不自動代表每張工單都由他處理
  • 把群組加入共用 scheme 的修改可能超出單一專案範圍
  • 加 request participant 不是安全層級的通行證

02.01 佇列配置與 JQL 排錯

  • Queue 的消失不等於工單被刪除
  • 最後一輪 breached 與歷史 everBreached 不相同
  • 未加 remaining 下界可能把逾時項目也放進「即將逾時」
  • 側邊計數與實際查詢結果可能有更新時機差異

02.02 Configure SLAs 設定服務等級協議

  • 「4h 就是建立後四個實際小時」：只有服務時段與條件真的允許持續計入時，兩者才相同
  • 「沒跑就是 Pause condition 成立」：也可能只是行事曆外
  • 「符合兩個 goal 就採最嚴格的那個」：要先看順序，不是比較哪個數字最小
  • 「Done 一定滿足 Resolution: Set」：需要查欄位與事件
  • 「客戶回覆必然解除等待」：若工作流程沒變，暫停條件仍可能成立
  • 「優先順序升高就從零開始」：既有累計時間會計入新目標

規則來源分別見前面的心智模型、疑難排解與變更行為；這些句子是教學歸納，不是官方試題原文。

02.03 功能開關與 ITSM 工作類別

  • 看到 board 不代表已建立完整 Kanban 工作方法
  • 工作 calendar、SLA calendar、值班 schedule 不可互換
  • Incident priority 與 alert priority 可以不同，且映射可能影響多個服務專案
  • Feature lab 不是永久可用功能的保證

02.04 值班排程、路由與升級

  • 把一般 routing 放第一條，會遮住後面的特定條件
  • 直接送 schedule 不代表設好了後援升級
  • Ack 不等於 Close；要讀每一步的狀態條件
  • No one 仍可留下警示紀錄；也可能造成無人值班或無通知的風險

03.01 在請求中使用 Assets

  • 同名文字不等於同一個 object 參照
  • 能看工單不代表應公開整個資產資料集合
  • 不能用 Cloud Assets 欄位直接排序 JQL 結果
  • 舊文件的 Premium-only 說法不能取代目前 Service Collection 方案查核

03.02 服務目錄、責任角色與服務分級

  • 原生 Affected services 不是任何 portal customer 都能直接填寫的欄位
  • 設 owner、tier 或關係不等於已通知、已提高優先度或已建立核准關卡
  • 服務圖僅呈現已建的關係，缺少連線不能證明沒有依賴
  • 新 Services 的編輯權需核對 Assets，不能只看 project admin

03.03 產品與支援資格

  • 有 customer 帳號不代表有所有產品 entitlement
  • 加到整個 organization 的資格範圍比單一客戶大
  • 到期日 detail field 不自動等同自動停用政策
  • Required 不應被擴大解釋為所有管道及所有契約限制的通用安全控制

04.01 請求類型與欄位呈現

  • 把「藏出 portal groups」當成安全限制
  • 為單一表單需求修改共用 field configuration，卻沒有檢查其他管道
  • 誤認顧客狀態別名會改變底層 workflow
  • 為 email 或 virtual agent 使用的類型加入不相容的 Restrictions

04.02 表單 條件邏輯與欄位連結

  • 同名 form field 被誤認為已連上 Jira field
  • 把必填欄位藏進條件區段
  • 把 Internal 表單預期成客戶已可填寫
  • 把 shareable 理解成任何人都可存取
  • 把 PDF 快照、表單鎖定或推薦呈現誤認為工作流程完成

  • 假設網域規則會自動比對所有子網域
  • 把停用寄入 email 當成停用寄出通知

04.04 工作流程 入口轉換與核准

  • 修改共用 workflow 卻只測一個 request type
  • 用 portal transition 的 validator 當唯一資料保護

05.01 客戶入口 公告與多語

  • 將 portal logo 與 space avatar 混用
  • 把某 portal 的公告權限理解成所有 help center 管理權
  • 為了 widget 任意公開內部知識庫
  • 誤認新增語言或改原文後，所有自訂內容與 email templates 已自動翻好

05.02 Virtual service agent 與知識庫回答

  • 將 virtual service agent 等同任何 Rovo agent
  • 預設入口藏起來或有代理無法取得的必填資料
  • 用訓練語句代替解題流程，或將意圖命中率當解決率
  • 為啟用 AI 任意放寬正式文章權限
  • 在不知道會立即生效的情況下啟用 intent 或 AI answers

05.03 通知與共用回覆

  • 以管理員自己的收信情形代替純 customer 測試
  • 將內部 note、公開 reply 與所有人的網路公開混淆
  • 把狀態名稱 Done 當成 Resolution 必然已設定
  • 為美觀移除主旨的 work item key，或亂改變數語法
  • 把沒有失敗 log 當投遞成功證明

06.01 知識庫連線與權限

  • 管理員看得到就認定顧客也能看
  • 把 Unlink 當成刪除或撤銷所有途徑的閱讀權
  • 為修復一位顧客的問題而任意選 Anyone
  • 將 All logged-in users 理解為只限特定組織
  • 把 JSM service space 與 Confluence space 當成同一容器

06.02 文章建議與內容組織

  • 把跨站來源可連結誤認為每種功能都支援
