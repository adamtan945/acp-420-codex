02.04 值班排程、路由與升級

本課適用 Jira Service Management Cloud，以 company-managed 服務專案為主要情境。新版文件可能寫 service space、work item、work type；考綱仍使用 project、issue、issue type。教材保留兩套名稱，不把新名稱直接代入 JQL。所有人物、工單和設定數值都是原創教學案例。

讓警示找得到人，還要知道沒人接時怎麼辦

值班（on-call）的目的不是列出團隊成員，而是把某段時間的回應責任清楚交給某個人或一組人。當網站監控出現異常，通知應找目前值班者；若無人確認，按約定尋找後援。這一課將 schedule、rotation、routing、escalation 和 alert policy 分開設計，再把它們接起來。

先備詞彙：schedule 是值班排程；rotation 是輪替規則；override 是某一時間段的臨時代班；routing rule 是依警示內容或時間選擇接收路徑；escalation policy 是按延遲與警示狀態逐步通知；acknowledge（ack）表示有人確認收到／接手警示，close 表示結束警示，兩者不是同一狀態。

02.04.01 排程包含時區、起點、覆蓋與代班

建立排程前先寫清楚服務責任：是否全年無休、使用哪個時區、何時交班、誰在名單內、有無休假代班。排程的時間只是責任安排，不能保證通知一定送達；接收人的通知偏好、整合狀態與後續規則仍要驗證。 官方來源：create an on call schedule

團隊管理員可從團隊的 Operations → On-call，在 Schedules 旁選新增，指定排程名稱與時區，建立後 Add rotation。參與者順序、班次範圍、Shift frequency 和開始時間一起決定未來誰值班。務必看 schedule preview，至少檢查本週、跨週交接與非上班時段，而不只看第一天。網站級 schedule 則有額外的 Product admin／Operations global admin 角色要求；本課預設做團隊級教學配置。 官方來源：create an on call schedule

臨時請假時可加 override，指定起訖時間、時區、適用 rotations 與代班者。Override 是覆蓋某一段責任，不必改掉整個長期輪替順序。若選 No one，該段可能無人值班，這不是「隨便選一個保留空白」的無害選項。設定後應從排程時區查看實際結果。 官方來源：override an on call schedule

02.04.02 Rotation 決定輪替，routing 決定哪個警示使用它

一個 schedule 可有多個 rotations，各有參與者與時間範圍。例如白天輪替由 A、B，夜間輪替由 C、D；也可能用第二個 rotation 表示備援。設計時要主動確認重疊是否有意，以及空窗是否違反服務承諾。Daily、Weekly 或 Custom 描述輪替與班次安排方式；不要單靠選項名稱猜實際覆蓋時間。 官方來源：create daily weekly and custom rotations

Routing rules 在警示交給團隊時，依來源、內容或時間決定送往哪個 schedule、escalation 或 No one。系統由上往下採第一個符合的 routing rule，因此較特定的 P1 條件通常應放在一般條件之前。這是條件設計原則：不是因為規則叫「緊急」就有特別高的系統優先權。 官方來源：What are routing rules?

如果 routing 指向 schedule，就通知警示建立時正在值班的人；未確認時不會因此自動升級。若 routing 指向 escalation，便由該政策決定後續通知順序。指向 No one 仍會保留警示讓團隊看見，只是不通知；所以「沒有收到通知」不能直接推論「警示沒建立」。 官方來源：What are routing rules?

目前文件對方案有明確限制：Free／Standard 只能建立一個自訂 routing rule，多個自訂規則需 Premium／Enterprise。此處只把它作為查核日的限制；練習如需多條規則而方案不支援，改做紙上排序推演，不宣稱已實作。 官方來源：create edit delete a routing rule

02.04.03 Escalation 需要時間、接收人與停止條件

Escalation 適合「先找當班者，五分鐘仍未確認就找後援」。每個步驟都要定義在多久後檢查、要通知誰，以及警示要處於什麼狀態才執行。Not acknowledged 與 Not closed 的選擇非常重要：已 ack 但尚未 close 的警示，可能不再符合前者，卻仍符合後者。不能把「有人按 ack」說成所有自訂政策必然立刻停止。 官方來源：What are escalation policies? 官方來源：create edit delete an escalation policy

團隊管理員從 Teams → 該團隊 Operations → On-call → Escalation policies 新增，逐步設定 rule 並儲存。原創教學政策：立即通知「教學主要排程」的 on-call member；五分鐘後若仍 not acknowledged，通知指定教學備援人 B。這裡使用明確的測試備援人，不依賴某些方案才支援的 next user、random member 或 repeat。 官方來源：create edit delete an escalation policy 官方來源：What are escalation policies?

有些站台支援 repeat 及自動關閉，但這些是額外行為，可能造成持續打擾或在無人處理時結束警示。初學時先用兩個容易驗證的步驟，釐清條件與結果，再學更複雜政策。不能將升級等同自動修復服務。

02.04.04 Alert policy 在建立警示時調整內容與屬性

Alert policy 用條件識別警示，在建立時調整內容、描述、priority 或 responders 等屬性。它解答「進來的這種訊號，要以什麼資料形成警示」。Routing 則解答「交給這個團隊的警示，要走哪條通知路徑」。因為政策也能改 responders，兩者會相互影響，但不是同一個設定頁。 官方來源：What are alert policies?

從團隊 Operations → Policies → Alert policies → Create alert policy，填名稱、Alert filters、必要的時間限制，再設定 Alert properties。可選是否立即啟用；初學練習先不要勾選啟用，完成審閱後才在隔離通知環境測試。若要修改全域政策，必須具對應網站管理權，並了解會影響其他團隊。 官方來源：create edit delete an alert policy

官方文件指出全域 alert policies 優先於團隊政策，同層由上往下比對。若多個政策看起來都符合，不應假設它們一定會依序累加或最後一個覆蓋一切；應讀取實際配置與警示 activity log，查出真正套用的政策。Activity log 會記錄政策應用，是觀察結果的關鍵證據。 官方來源：What are alert policies?

完整原創案例：教學借書服務

需求：教學警示標籤為 library 且 Priority 為 P1 時，要由主要排程接手；五分鐘未 ack 就通知備援。一般資訊型 P5 留紀錄但不打擾。A 和 B 每日輪替，時區 Asia/Taipei；A 某天下午由 B 代班。所有接收者都是明確核准的測試帳號，沒有真實電話、簡訊或正式 chat 連接。

  1. Team admin 建立「教學主要排程」，時區 Asia/Taipei，加入 A、B，每日輪替。預覽兩天的交班邊界，確認凌晨前後責任落在正確人
  2. 針對教學指定日期 13:00–17:00 加 override 給 B；檢查只改該時段，前後長期輪替保持原本安排
  3. 建立「教學緊急升級」：第一步通知主要排程，第二步五分鐘後仍未 ack 時通知 B。先確認 B 是否同時當班，以免案例實際只通知同一人
  4. 若方案允許多規則，把 P1 且 library 的 routing 放前面並指向該 escalation；低優先資訊規則依設計指向 No one；一般後備規則放最後。若方案只允許一條，自訂只保留緊急規則，其餘以紙上表列，不宣稱建成
  5. 建立但先停用一個 alert policy：符合教學來源時，將訊息加上「TRAINING」標記。確認它不改真實來源、priority 或全域接收人，再在核准隔離情境啟用
  6. 模擬四個輸入：P1/library、P5/library、P1/非 library、P1/library 在代班時段。逐一寫出預期政策、routing、on-call 人員及五分鐘後結果
  7. 只有在通知目的地已驗證為測試環境後才實際建立測試警示。檢查 activity log、接收對象與時間；另做一張在兩分鐘 ack 的測試，預期 not acknowledged 的第二步不再執行
  8. 最後停用本次教學政策並依約保留測試紀錄；不刪除真實警示或更動正式排程。若沒有可安全通知的隔離環境，交付紙上預期矩陣即可，明示未實測

配置來源見排程、代班、路由、升級與政策官方文件。五分鐘、人物與標籤均為本課自行設計的情境，不是服務承諾建議。 官方來源：create an on call schedule 官方來源：override an on call schedule 官方來源：create edit delete a routing rule 官方來源：create edit delete an escalation policy 官方來源：create edit delete an alert policy

排錯：有警示但沒人接，逐層定位

先查警示是否建立以及套用哪個 alert policy；再查團隊、routing 第一個匹配條件與目標；接著核對建立時刻的排程時區、rotation 和 override；然後檢查 escalation 在當時是否符合 not acknowledged／not closed 條件；最後核對接收人的通知設定。這樣可以把「輸入沒進來」、「路由選錯」、「無人值班」、「升級已停止」、「通知沒送達」分成不同問題，而不是每次都加一位全域管理員。 官方來源：What are routing rules? 官方來源：What are escalation policies? 官方來源：What are alert policies?

  1. 第一條，因 routing 採第一個符合；應把例外條件放對順序。2. 不一定，需看條件是否為 not closed 及其他配置。3. 先考慮有明確起訖與代班人的 override，再驗證覆蓋。

重點回顧

Schedule 回答何時由誰值班，rotation 建立週期，override 處理暫時例外，routing 挑路徑，escalation 處理沒人接或尚未關閉的後續，alert policy 調整警示建立時的屬性。

常見陷阱

  • 把一般 routing 放第一條，會遮住後面的特定條件
  • 直接送 schedule 不代表設好了後援升級
  • Ack 不等於 Close；要讀每一步的狀態條件
  • No one 仍可留下警示紀錄；也可能造成無人值班或無通知的風險

觀念釐清

排班正確、選對通知路徑與接收人實際收到，是三個要分別驗證的結果。一張預覽排班圖不能代替整條通知鏈的測試。

文件限制與待實機核對

本課未建立真實警示、排班、電話通知或第三方整合。不同 Operations 入口、方案及管理角色會影響可用功能；官方 rotation 文章的 weekly 範例有部分文字不一致，因此以明確設定值與 schedule preview 驗證，不照抄矛盾步驟。
