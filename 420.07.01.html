07.01 用 JQL 找到真正需要處理的請求

認證：ACP-420｜考綱：V2 April 2025｜領域：Reporting 7%｜內容查核：2026-10-05 覆蓋：07.01.01、07.01.02、07.01.03。以下配置教學以公司管理型 JSM Cloud 為主；只在獲准的隔離練習環境操作。教學中的 SUPPORT、CloudDesk、Review queue 皆為虛構資料。

你會學到什麼

客服主管說「給我需要注意的案件」，這句話還不足以建立一張可用清單。你得把「哪個服務專案、目前什麼狀態、哪個服務承諾、要不要包括過去曾逾時」說清楚。JQL（Jira Query Language）就是描述這些篩選條件的語言。它用來找資料；單純執行查詢不會更改工單，也不會替人增加閱讀權限。

本節先讓從未寫過查詢的人看懂基本句型，再學 JSM 專有的核准、SLA 與產品資格查詢。最後保存篩選器供工作使用，並檢查 AI 產生的查詢是否真的符合需求。

先備概念與小字典

  • Work item：Jira 儲存的一筆工作。考綱常稱 issue。JSM 的顧客請求會對應工作項目，但不是所有一般 Jira 工單都自動成為可在顧客入口使用的請求
  • Field：這筆資料的欄位，例如 project、priority、assignee。SLA 也可以作為可查詢的欄位
  • Operator：比較方式，例如等於、屬於某個集合
  • Function：依條件計算或挑選結果的函式，例如 approved()。括號不可省略
  • Filter：已儲存的查詢。它保存如何找資料，並不是把當時的工單複製到另一個資料夾
  • Result：你執行查詢時可以看到的符合資料。不同權限的人可能得到不同結果

以上是理解本節的先備知識；完整 JQL 語言規格不是這一個目標的全部要求。JQL 入門、儲存搜尋

第一層 找資料的句型

最簡單的句型是「欄位、運算子、值」。例如 project = SUPPORT 表示只選這個虛構專案；priority = High 再限定優先順序。多個條件用 AND 表示都要符合，用 OR 表示符合其中一種即可。複合需求主動加括號，不讓讀者猜分組。

例如「SUPPORT 專案中，High 或 Highest 優先順序的工單」，可寫成 project = SUPPORT AND priority IN (High, Highest)。這比把三個條件隨手用 OR 串起來更能保留範圍。若實際網站的優先順序名稱不同，請改用該站已存在的值；不是照抄範例就保證找得到。

排序和篩選也要分開看。ORDER BY priority DESC, created ASC 只影響結果的先後，不會把工單優先順序真的改掉。每次新增條件後先核對少量已知資料，逐步建立查詢，比一次貼入很長的句子更容易找錯。

另一個常見落差是空值：assignee != currentUser() 不代表自動包括未指派的工單。若需求要包含未指派者，必須把 assignee IS EMPTY 的情境寫出來。這是查詢語意，不是資料遺失。官方 JQL 函式與空值說明

第二層 核准狀態不能只看工作流程名稱

approved() 用在 Approval 類型欄位，找出核准有最終通過決定的請求。常見示例句型為 approvals = approved()，但欄位的實際名稱應以站台為準。不要把 status = Approved 當作完全相同：狀態只是流程中的一個值，可能有團隊自訂的同名狀態，未必是原生核准欄位的最終決定。

pending() 則可幫你找仍在等待核准的請求。選函式前先問：我要「已經核准」、「任何時候曾被指定為核准人」，還是「目前等我核准」？這些業務問題不同，不要只因都含 approval 就混用。

用三張虛構資料驗證：A 有最終核准通過；B 仍等待；C 只有工作流程名稱叫 Approved、沒有已完成核准資料。查詢「核准已通過」應符合 A。若 C 也出現，先檢查你是否其實查了 status。

來源：JSM JQL functions

第三層 SLA 函式描述的是不同時間範圍

假設自訂 SLA 名為 Support resolution time。名稱有空格時，查詢使用直式雙引號，不要從排版文字誤貼彎引號。

  • "Support resolution time" = breached()：查看最近一個 SLA 週期是否沒有達標
  • "Support resolution time" = everBreached()：找有過逾時紀錄的工作項目
  • "Support resolution time" = paused()：目前週期因設定的 Pause 條件暫停
  • "Support resolution time" = completed()：週期已達到完成條件

這些不是四種互相替代的字。某請求第一次處理曾逾時，重新開啟後的最近週期達標，問「曾經」和問「最近」會得到不同答案。另一方面，沒有增加時間也可能只是行事曆外；不要直接推斷 paused() 一定成立。上一節 SLA 的雙軌時間線就是用來區分這些原因。

實際排查先選一張你知道歷史的請求，對照工單 SLA 記錄，再選函式。不要以清單總數碰巧相同，就判定兩個函式意思一樣。

來源：SLA 專用 JQL

第四層 產品資格查詢

在支援 Products／Entitlements 的既有 JSM 環境中，entitlement IN entitlementProduct("CloudDesk") 是查找與指定產品資格關聯之工作的句型。函式回傳的是可配合 Entitlement 欄位使用的集合，因此要核對支援的運算子，不能把 IN 任意改成 =。

此處的產品不是一般 Jira project 名稱，也不是工單 summary 中出現同樣文字。產品資格是結構化關聯；若只在描述寫「CloudDesk」，不代表已設定 Entitlement。

版本限制很重要：官方文件指出新網站在 Service Collection 推出後，相關客戶服務功能移到 Customer Service Management。考綱仍列此知識，教材保留概念；新站找不到 JSM 開關時，先辨識產品環境，而不是立刻要求更高權限。這節不把 CSM 新版操作路徑混成 JSM 舊路徑。

來源：函式語法、JSM 產品與支援資格的環境註記

實作 把查詢保存為工作入口

前提：有權閱讀示範資料的測試帳號。保存自己的 filter 與分享給其他人是不同動作；分享還需要網站允許的權限。不要用本練習把真實公司資料對外公開。

  1. 從目前 Jira 搜尋入口開啟工作項目搜尋，切換至 JQL／進階查詢
  2. 先輸入 project = SUPPORT，確認只有示範專案結果
  3. 依需求加入核准或 SLA 條件，使用已知測試資料檢查「應包括／應排除」各一張
  4. 再加入排序；檢查排序只改顯示先後
  5. 以 Save as／儲存搜尋建立私人 filter，名稱說清楚目的，例如 SUPPORT 最近週期逾時
  6. 重新開啟 filter，確認它保留查詢；改變一張測試工單後重新查詢，理解 filter 會依目前資料產生結果
  7. 在獲准的隔離環境才示範分享設定：開啟 filter 詳情，檢查檢視者與編輯者。先分享給最小測試群組，不選公開選項
  8. 使用另一測試帳號開啟同一 filter。若它可開啟 filter 卻看不到部分工單，回到工單權限檢查，不把「分享查詢」當成「分享全部資料」

目前名稱與入口會隨導覽更新不同；本文以官方文件核對，未登入使用者站台驗證按鈕位置。管理 filters、進階搜尋

使用 AI 產生 JQL 還要做什麼

目前介面文件稱此功能為 Rovo；考綱使用 Atlassian Intelligence。你可以先以自然語言描述需求，再檢查產生的 JQL。好的描述要包含專案範圍、狀態或日期、SLA 的「最近／曾經」及排序要求。

例如描述「找SUPPORT專案最近SLA週期逾時的請求，較早建立的排前面」，生成後逐段檢查：專案是否正確、SLA 欄位是否存在、用 breached 還是 everBreached、有沒有多加不必要的狀態條件。最後仍用正反測試資料驗證。AI 產生可執行的語法，不代表它理解了你的服務政策；結果零筆也不是無問題的證明。

來源：Use Rovo to search for work items

問題一：主管要找「曾經逾時但最近處理已達標」的案件，只用 breached() 夠嗎？

查看答案與理由

不夠。要區分歷史與最近週期；先用 everBreached() 表達曾經，再按真正需求設計其他條件。

自我檢查

問題二：同事看得到你分享的 filter，卻比你少三張工單，先查什麼？

查看答案與理由

比較工單本身的可見性與查詢中的個人化函式，不要先公開所有工單或重建 filter。

摘要

JQL先界定資料範圍，再選正確欄位、運算子與函式。核准、SLA最近週期、SLA歷史、產品資格是不同概念。保存filter保留查詢，分享filter不會取代工單權限。AI查詢要驗證語意與實際結果。

常見陷阱

  1. 使用同名status冒充核准結果
  2. 把breached和everBreached混用
  3. 把行事曆外當成Pause條件成立
  4. 在應使用IN的資格函式上換成等號
  5. 將filter分享當作擴張資料可見性
  6. 直接信任AI產生或零筆結果

觀念釐清

Filter是搜尋規則，queue是供服務團隊處理工作的呈現，board是另一種工作視覺化。它們可以利用查詢，但不等於把工單搬到不同儲存空間。判斷篩選結果時，查詢條件和讀者權限都要檢查。
