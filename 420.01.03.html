01.03 服務團隊、指派與存取排錯

本課適用 Jira Service Management Cloud，以 company-managed 服務專案為主要情境。新版文件可能寫 service space、work item、work type；考綱仍使用 project、issue、issue type。教材保留兩套名稱，不把新名稱直接代入 JQL。所有人物、工單和設定數值都是原創教學案例。

一個人加入團隊後，為什麼還可能不能接工單？

加入服務團隊涉及三件不同的事：帳號是否具備 JSM agent 產品存取、在此專案是否屬於合適角色，以及該角色在目前權限方案裡能做哪些動作。公司新進工程師只需要回覆內部診斷，和值班客服需要正式對外處理，設定不應相同。本課會先管理團隊，再追查 assignee，最後以最小變更排除存取問題。

先備詞彙：Service Desk Team 是 JSM 預設專案角色；permission scheme 是把動作分派給角色的共用設定；project lead 是專案負責人；default assignee 是新工作項目的預設指派方式；component 是同一專案內可用來分類工作的元件；issue security level 是單張案件採用的安全層級。

01.03.01 加入或移除 agent 與 collaborator

以 space admin 進入 Space settings → Access → People and access，選 Add people，指定已核准的測試使用者或群組及 Service Desk Team 角色。既有成員可在 Role 欄選取／取消角色；移出專案可使用 Remove。一人可以有多個角色，因此移除一列或取消其中一個角色後，仍要檢查是否經其他群組或角色持續取得存取。 官方來源：Manage service project role memberships

Agent 需要適合的 JSM 授權；collaborator 是具其他適當 Jira 授權、在允許範圍協助的人。加入 Service Desk Team 只是專案角色配置，不能代替 app access 的授權管理。移除專案角色也不等於取消整個網站的產品授權；如果目的只是離開這個服務團隊，不應順便撤銷他仍在其他專案工作的帳號。 官方來源：What are space roles in Jira Service Management? 官方來源：Manage service project role memberships

01.03.02 讓開發者加入內部討論

原創案例：測試客服珊接到「登入失敗」，需要測試開發者岳確認錯誤。岳不負責直接答覆客戶。管理員應核對岳的 Jira 產品存取，將他加入教學專案 Service Desk Team，並確認權限方案及案件安全性允許他查看、加內部留言。岳的意見由珊整理成公開回覆。 官方來源：What are space roles in Jira Service Management? 官方來源：How can service project and software teams work together?

這樣做保留服務責任的清楚界線：診斷由懂技術的人提供，承諾與客戶溝通由 agent 負責。不要以「把岳加為 request participant」代替內部協作，因為 participant 主要走 portal 的客戶可見對話；也不要為了看一張測試單就授予 Jira 管理權。

01.03.03 用角色成員管理專案動作

Jira admin 在 permission scheme 中把 Browse、Edit、Add Comments 等動作授給角色；space admin 再把合適的人放入角色。你可以想成 Jira admin 決定「這把鑰匙能開哪些門」，space admin 決定「目前把鑰匙交給誰」。這使同一方案在多個專案共用時，仍能保有不同團隊名單。 官方來源：Customize Jira Service Management permissions

改角色成員和改 scheme 的影響範圍不一樣。把測試客服加進本專案 Service Desk Team，是本專案成員異動；改一份多專案共用的 permission scheme，可能同時改變所有採用它的專案。先辨識原因，再選較窄的修改；不要為了一個遺漏的成員而修改全站共用方案。

JSM 有必要的角色與 portal 安全類型配置。尤其 customer 權限要透過 Service Desk Customer - Portal Access；若改成直接對一般群組授權，部分服務功能可能失效。修改後不只測試 agent，也應測試 customer 提交、留言與附件行為。 官方來源：Customize Jira Service Management permissions

01.03.04 Project lead 和 default assignee

Project lead 記錄服務專案的負責人，不等於每張工單的 assignee。Default assignee 決定新案件在沒有明確指定時的預設處理方式，常見選擇是 Project lead 或 Unassigned。設定前要確認 lead 本身具有 JSM agent 授權與 Assignable User 權限；否則不只是指派失敗，甚至可能造成請求無法建立。 官方來源：assign-failure

在公司管理的教學專案設定 Details 中核對 project lead 與 default assignee（新版可能以 Space details／owner 表示）。選 Project lead 時，準備用新測試單驗證；選 Unassigned 時，網站需允許未指派案件，而且團隊要有確實巡查的未指派佇列。這兩種設計沒有一種永遠正確：前者提供明確責任入口，後者適合由分流人員領單，但會增加漏接風險。 官方來源：assign-failure

01.03.05 五種指派來源與追查順序

手動指派適合已知道由誰處理的個案。建立時若明確選了某位符合資格的 assignee，便不應再把結果錯認為 project default。Automatic 代表讓 Jira 依預設邏輯決定；若有 component，component 的 default assignee 可能覆蓋專案預設。Component lead 是該元件的責任人，與 project lead 可以不同。多個 component 的複雜優先規則屬進一步設定細節，先用單一 component 掌握基本因果。 官方來源：assign

請求類型也可把 Assignee 設為隱藏預設值（preset value），讓「教學：館際借閱帳號」每次先交給指定 agent。此設定在 Request types → 選請求類型 → Request form 中維護。隱藏表示客戶不需要選擇負責人，不表示 assignee 被省略或取得額外權限。使用前須確認欄位可用及預設對象可被指派。 官方來源：request-customize 官方來源：Customize Jira Service Management permissions

自動化（automation）可以在建立或欄位改變等事件後重新指派。因此問題「為什麼原本是珊，幾秒後變成岑？」不能只看當下預設值。先看工作項目 History 的欄位變更時間與操作者，再看相關 automation audit log。預設邏輯處理建立時的空缺；後續規則是另一個事件來源，並不存在適用所有站台的固定五層覆蓋順序。規則本身的建立與稽核在第 08 領域完整教授。 官方來源：Debug an automation rule

原創追查案例：教學請求類型預設珊；Automation 在 label=network 時指派岑。送出一張帶 network 的測試單，若歷程先珊後岑，就應檢查該規則是否符合需求；反覆把 project lead 改成珊不會消除後續規則的效果。

01.03.06 用角色限制單張敏感工單

專案有「一般支援」與「封閉教學案件」。Jira admin 可在 issue security scheme 中定義安全層級，把特定專案角色列為可見主體，再將方案關聯到教學專案。具 Set Issue Security 等必要權限的人才能在案件上選擇適用層級。在 Free 網站，角色與安全性方案的編輯受方案限制；需先確認教學方案可用。此處先使用管理員已準備的安全層級，避免新手修改其他專案共用設定。 官方來源：Configure work item security schemes 官方來源：Permissions limitations in Free Jira sites

如果安全層級只包含「教學受限處理員」角色，普通 Service Desk Team 成員即使能瀏覽專案，也可能看不到這張案件。反過來，僅被列入安全層級但缺少專案基本瀏覽權，也不能靠安全層級繞過專案門檻。客戶、reporter 與 request participants 是否仍能看這張請求，必須有意識地設計；尤其 participants 仍受安全層級約束。 官方來源：access-troubleshoot 官方來源：participants

把已核准的角色放入教學安全層級

由 Jira admin 進入 Settings → Work items → Work item security schemes，選只供本次教學的方案與安全層級，使用 Add 將「教學受限處理員」這個既有 project role 加入允許查看的成員範圍。不要修改正式共用方案；安全層級允許的角色、reporter、portal access 等應由教學管理員事先審核，避免把合法客戶鎖在外面。 官方來源：Restricting Queue Access in JSM Cloud

在已關聯該安全性方案的教學專案內，具必要權限的人開啟工作項目，選右上方鎖頭／Set security level，挑教學層級。若沒有鎖頭，先查方案關聯與權限，不先建立同名文字欄。套用後，用有該角色與無該角色的獨立 agent 帳號開啟同一張測試單，分別驗證能看見與不能看見。 官方來源：Create work items and subtasks

01.03.07 按層排錯，比一次全開更可靠

第一步確認使用的帳號：瀏覽器可能登入了另一個測試身分。第二步檢查產品：要做 agent 動作的人是否具 JSM 存取。第三步檢查專案角色與 permission scheme：能瀏覽不代表能指派，能指派別人也不代表自己符合 Assignable User。第四步檢查特定工作項目的安全層級。最後才核對畫面限制、request type、portal 分享及動作所需其他條件。 官方來源：What are space roles in Jira Service Management? 官方來源：Customize Jira Service Management permissions 官方來源：assign-failure 官方來源：access-troubleshoot

把問題寫得具體：「岳能開一般測試單，只有 LIB-7 看不到」比較指向單張安全性；「珊所有 JSM 專案都不能用 agent 畫面」比較指向帳號或產品存取；「珊看得到案件但不能把岳設為 assignee」則要查岳的授權與可指派性。這是診斷順序，不是繞過權限的作法。

隔離練習：建立、轉交與受限案件

前提是教學網站的既有權限方案已由管理員核准，測試 agent 珊／岑及 collaborator 岳皆為專用帳號。練習不連接真實通知或真實客戶資料。建立前記錄原有 project lead、角色成員與預設指派設定，方便在同一隔離環境恢復。

  1. 在 People and access 加入珊為 Service Desk Team，核對其 agent 授權；加入岳為 collaborator，測試他可對普通測試單加入內部留言
  2. 由管理員在 Details 將 lead 設為珊、default assignee 設為 Project lead。建立一張不帶 component、不帶特殊預設值的測試請求，確認 assignee 為珊
  3. 改用帶有單一教學 component「網路」的建立情境；該 component 預設指派給岑。建立時採 Automatic，觀察新單是否由岑接收。不要在同一測試中同時加第二個 component
  4. 在單一教學 request type 設定隱藏 Assignee 預設珊，送出新單並記錄歷程。若另有指派規則啟用，先在教學環境停用或明確列入測試條件，避免混淆變因
  5. 使用已設定好的「教學受限處理員」安全層級，對第二張測試單套用；以有該角色與無該角色的兩個 agent 分別開啟，確認正向與反向結果
  6. 從教學專案移除岳的直接角色，檢查他是否仍透過群組繼承相同角色。這一步只移除教學專案存取，不刪除帳號或全站授權

完成時應能交出「設定來源→觀察到的 assignee／可見性→驗證帳號」紀錄。若安全層級的設定入口不可用，交由 Jira admin 檢查；不要改正式專案來試。 官方來源：Manage service project role memberships 官方來源：assign 官方來源：assign-failure

重點回顧

成員管理以角色為中心，產品授權另行核對；預設指派要有可被指派的人；排錯先分清建立時與後續變更，再逐層驗證存取。

常見陷阱

  • 專案角色名單的 Remove 不代表刪除帳號，也未必移除群組繼承權
  • Project lead 不自動代表每張工單都由他處理
  • 把群組加入共用 scheme 的修改可能超出單一專案範圍
  • 加 request participant 不是安全層級的通行證

觀念釐清

Assign Work Items 是能執行指派動作；Assignable User 是某人可以成為負責人。兩者問題不同，且 JSM assignee 還需符合 agent 授權條件。教學中問「誰不能做什麼」比只問「權限有沒有開」精確。

文件限制與待實機核對

未測試租戶實際的 issue security scheme、request preset 與 automation 交互作用。多 component 的細節與新版 owner 名稱需依該站台版本核對；本課實驗刻意使用單一 component，不將一般 Jira 文件的全部情境無條件套用到每一種 JSM 專案。
