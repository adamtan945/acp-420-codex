01.01 身分、角色與多層權限

「內部／外部」描述情境，不是固定的員工名冊分類。同一個人可在一個服務專案當 agent，又在另一個服務專案當 customer。最終判定以這次使用的帳號、產品權限、專案權限及案件關係為準。

網站層 customer access 是各專案的可用邊界；專案 customer permissions 是在邊界內決定如何服務。二者不是重複的同一個開關。

01.03 服務團隊、指派與存取排錯

Assign Work Items 是能執行指派動作；Assignable User 是某人可以成為負責人。兩者問題不同，且 JSM assignee 還需符合 agent 授權條件。教學中問「誰不能做什麼」比只問「權限有沒有開」精確。

02.02 Configure SLAs 設定服務等級協議

把一個 SLA 想成「帶規則的碼表」：

  • 條件決定週期邊界與暫停狀態
  • 目標用 JQL 選擇適用工作項目，並指定時間上限與行事曆
  • 行事曆提供時區、工作日、服務時段與假日

在本課的固定目標案例中，累計時間就是：啟動後、結束前，同時位於工作時段且未符合暫停條件的時間總和。這是依官方條件與行事曆規則整理的教學模型；同一分鐘即使同時是午休和等待客戶，也只排除一次。條件 · 目標 · 行事曆

04.01 請求類型與欄位呈現

顧客的 Request form、提交後 portal 詳細資料、agent 的 Work item view 是三個不同觀察位置。欄位出現在其中一處，不足以推論另外兩處的可見性或編輯能力。

Request form 是客戶入口的完整填寫畫面，Form 是可附加且有自己欄位與狀態的表單。Automation 附表到一張 work item，與管理員把表單配置到某個 request type，是兩件不同的事。

04.04 工作流程 入口轉換與核准

核准是一個具有來源、門檻與結果的決策機制；轉換是移動狀態的動作。兩者可以配合，但名稱相同的按鈕或狀態不代表相同權限與效果。

Filter是搜尋規則，queue是供服務團隊處理工作的呈現，board是另一種工作視覺化。它們可以利用查詢，但不等於把工單搬到不同儲存空間。判斷篩選結果時，查詢條件和讀者權限都要檢查。
