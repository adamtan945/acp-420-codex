02.03 功能開關與 ITSM 工作類別

適用範圍、版本用語與案例前提

本課適用 Jira Service Management Cloud，以 company-managed 服務專案為主要情境。新版文件可能寫 service space、work item、work type；考綱仍使用 project、issue、issue type。

教材保留兩套名稱，不把新名稱直接代入 JQL。所有人物、工單和設定數值都是原創教學案例。

開啟功能前，先知道你想改善哪一種工作

功能開關（feature toggle）決定某些工作能力及導覽是否可用。開啟新功能不會自動完成整套服務流程：出現 On-call 入口後仍要排班；出現 incident 類別後仍要設計請求類型與責任；新增 board 後也不代表工作流程已經正確。

本課的目標是能選對功能、說明影響，再驗證開關是否真的支援團隊需求。

先備詞彙：ITSM 是 IT service management；incident 是需恢復服務的事件；alert 是提醒系統或人員注意問題的警示；responder 是參與處理事件／警示的人；feature lab 是可試用但仍可能變動的實驗功能區。

02.03.01 Features 入口與權限不是所有項目都相同

從服務專案旁 More actions → Space settings → Features 檢查可用功能。某些功能只需 space admin，另一些要 Jira admin 或更高層角色；不能把「我可開 Views」推論成「我能改所有 Operations 功能」。

目前官方文件指出 Alerts、On-call 可加入各種服務專案，而 Services 僅適用 ITSM spaces；啟用該組功能的文件要求 Jira admin。

官方來源：Add Services, Alerts, and On-call to your sidebar

開啟後回到側邊欄，應看見相應的導覽項目，再完成後續設定。停用前先閱讀當前畫面的提示：隱藏入口、停用一項能力、刪除既有資料不是同一件事，不能承諾所有開關的資料行為都一樣。教學練習僅在隔離網站記錄切換前後的導覽、既有測試工作項目和配置狀態；遇到會影響資料或外部連接的確認畫面，先停下來理解後果。

02.03.02 board 與 calendar：相同資料的不同觀察方式

切換視圖不會自動創造另一張請求。

List 適合逐列分流；board 把工作項目依狀態等配置放入不同欄，適合看工作停在哪個階段。保留英文 board 和 Kanban：Kanban 是管理工作流的一種方法，board 是視覺工具；只開啟 board，不等於團隊已採用完整 Kanban 方法。

Calendar 把有日期資訊的工作放到時間位置，適合觀察預定處理或到期時程。它不是 02.02 的 SLA calendar，也不是 02.04 的 on-call schedule。三者分別是「工作何時發生的視圖」、「計時可累計的服務時段」、「誰在何時值班」。名稱相近，目的完全不同。

官方來源：Enable new views for your service space

目前可在 queue 的 List 旁使用 Add to navigation 加入 board 或 calendar；需要 Jira 或 space admin。另一個入口是 Features → Views，再從 Views 使用清單、board 或 calendar。

考綱要求能啟用並理解 board／calendar，不應只背一個舊版按鈕位置。新增視圖後，確認它顯示的是相同預期集合；行事曆沒有出現某張單時，先核對其日期欄位與篩選，不要先以為資料遺失。

官方來源：Enable new views for your service space

02.03.03 五種工作類別各自解決什麼問題

服務請求（service request）是要求已知服務或協助，例如申請新的教學測試帳號。事件（incident）是服務中斷或品質下降，例如整個借書入口無法登入，重點在儘快恢復。問題（problem）是追查事件的根本原因或潛在原因，例如多次登入失敗背後的連線耗盡。

變更（change）是規劃調整服務以控制風險，例如更新登入元件。事件後檢討（post-incident review，PIR）是在事件後整理影響、時間線、改善行動與學習。

官方來源：Add a work category to any of your service spaces

官方來源：What are problems?

官方來源：What are incidents?

官方來源：Main JSM features

同一次真實情境可能需要多種工作：先建立 incident 恢復服務，另建 problem 查根因，以 change 管理修復部署，再做 PIR 檢討。這些不是把同一張單改四次名稱就能取代的目的。反過來，一般「請幫我開帳號」通常不需要完整事件指揮流程。

先看工作目的，再選 category 與適合的 request type。

目前 company-managed 服務專案可以在 Features 開啟相關 work categories，team-managed 不支援相同的 category 模式。啟用後還要把相容的 request types 指派到類別，或建立新類型。

預期會增加相關 queue，對應 request types 的既有與新請求會出現在相關清單。

官方來源：Add a work category to any of your service spaces

方案也要區分：官方說明指出 major incidents、PIR 等進階事件能力自 2024 年 10 月起移到 Premium，部分 Free／Standard 舊專案的既有 request types／work types 仍有保留行為。

不要因為某個舊網站看得到 PIR，就說所有新 Standard 網站皆可完整配置相同能力。

02.03.04 警示、輪替、排程與升級如何接起來

系統監控可能產生 alert；要讓合適的人回應，需知道「發生什麼」以及「此刻誰負責」。Rotation 決定輪流值班的參與者順序與節奏；schedule 組合時區與輪替，給出某個時刻的值班人；routing rule 依警示條件選擇排程或升級政策；

escalation policy 在規定條件仍成立時，按時間通知後援。

官方來源：What are escalation policies?

02.03.05 用 chat 集中事件協作

Slack、Microsoft Teams、Zoom 等已核准的整合能把事件的處理人員集中到聊天或會議環境。以登入中斷為例，可在事件 Details 的連接功能建立或連結教學 channel／會議，加入必要 responders，在事件中保留診斷與決策。

外部聊天內容是否轉為 internal note 或客戶公開回覆，必須清楚區分，不能將內部技術討論不經檢查地對外發布。

官方來源：Use chat and video tools to resolve incidents as a team

這不等於讓所有 chat 訊息自動成為案件紀錄，也不代表安裝整合就是授權所有人閱讀敏感事件。先查整合範圍、接收者與存取權。零基礎練習以未連接的教學圖示完成；實際連接 workspace、授權 OAuth 或寄通知，需要獨立授權與測試目的地，不在本課預設執行。

02.03.06 Alert priority 與 incident priority 要做映射

Alert priority 通常用 P1 到 P5，P1 最高；incident 的 Priority 是工作項目上的優先等級。它們可以相同，也可以不同，以配合不同警示通知強度。

官方入口是 Space settings → Operations → Incident management → Assign alert priorities；設定由 Jira admin 管理，會影響使用事件管理的服務專案，因此不能把它當成無害的單張測試單修改。

官方來源：What are alert priorities?

原創映射案例：「重大事件」對應 P1，「高影響事件」對應 P2，「待觀察事件」對應 P4。這些名稱是教學自定值，不是官方預設。驗證時要比較事件欄位與實際產生警示的 Priority；僅在 incident 畫面看見 High，尚不足以證明警示會按 P2 發送。

提高 alert priority 可能重啟通知流程，因此切勿在正式警示反覆調整來試按鈕。

02.03.07 Feature lab：可以學習，不承諾永遠存在

Feature lab 位於 Features 內的相應區段。這些功能提供試用與回饋機會，但可能頻繁更新、表現不如預期，甚至不會正式推出。學習重點是知道如何在隔離環境驗證、記錄限制與回復方式；不用把某一天列出的實驗功能清單背成永不改變的考綱。

隔離練習：一個登入中斷的功能選擇

前提：空白教學 company-managed ITSM 專案，管理員已確認方案，沒有真實監控、chat 或電話通知連接。無實驗環境時用紙上決策完成，不需要購買方案來完成此課閱讀。

  1. 列出教學需求：一般帳號申請、登入中斷、事後根因調查。將它們分別對應 service request、incident、problem
  2. 在 Features 記錄目前開關與權限，啟用本環境可用的 work category。把一個適合的教學 request type 歸入該 category，回到 queue 觀察顯示結果
  3. 在同一教學 queue 加入 board 和 calendar。建立有明確狀態及教學日期的工作項目，確認 List、board、calendar 對同一項目的呈現差異
  4. 檢查 Alerts、On-call 與 Services 導覽是否符合網站類型及角色；先不建立任何會打擾人的警示
  5. 用紙上卡片安排「alert → routing → escalation → schedule → responder」，推演未確認時的後援路徑
  6. 只讀檢查 alert／incident priority 映射；若需修改，僅在核准的隔離網站由 Jira admin 進行。記錄它的跨專案影響
  7. 若 Feature lab 有可用項目，先讀說明再挑一項純教學測試；記錄如何停用及試用結果，不把可用性當正式承諾

可觀察結果應包括側欄／視圖改變、request type 與 category 關係、以及對通知影響的紙上預測；本課不聲稱已連接任何聊天或真實監控。

重點回顧

功能選擇從工作目的出發，並核對方案、專案類型與角色。開關只啟用能力或入口，真正可用仍需後續配置和驗證。

常見陷阱

  • 看到 board 不代表已建立完整 Kanban 工作方法
  • 工作 calendar、SLA calendar、值班 schedule 不可互換
  • Incident priority 與 alert priority 可以不同，且映射可能影響多個服務專案
  • Feature lab 不是永久可用功能的保證

觀念釐清

恢復服務、查根因、受控變更和檢討是不同目的。相互連結的工作項目能保留責任及歷程，比把所有活動塞進一種名稱更容易驗證。

文件限制與待實機核對

各 Feature 的開關、付費限制、資料保留行為與 rollout 需在教學租戶逐項確認。此課不假設所有開關可由同一管理角色切換，也不把 chat 或 Feature lab 畫面當成已實測。
