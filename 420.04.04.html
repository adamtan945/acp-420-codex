核准與取消走不同出口

核准是加在特定 workflow 狀態上的決策步驟，核准人可以來自預設值或顧客填寫的欄位。Portal transition 則是顧客可用的工作流程動作；它不能直接當成核准的同義按鈕。

用一個例子理解

虛構的「申請借用投影機」進入待核准，由測試岑核准後流向準備設備，被拒絕則流向拒絕。申請人小禾另能在 portal 取消申請。三條路徑必須各有清楚名稱與可觀察的最後狀態。

04.04 工作流程 入口轉換與核准

申請借用一台普通螢幕與申請借用昂貴攝影設備，可能需要不同的處理步驟。前者由服務團隊安排即可；後者在交付前要先取得負責人的核准。Jira 的 workflow（工作流程）把「目前走到哪裡」與「接下來可以去哪裡」明確表示出來。本課教你辨識這套流程，並分清顧客操作與正式核准。

名詞與角色

Status（狀態）是工作目前的位置，例如「待核准」。Transition（轉換）是由一個狀態移到另一個狀態的動作，例如「取消申請」。Approval step（核准步驟）是工作流程中的決策關卡；approver（核准人）必須符合設定並作出核准或拒絕。

Assignee（負責人）則是處理工作的人，兩者不必相同。

Request type（請求類型）連到 work type（工作類型，考綱稱 issue type），後者透過 workflow scheme（工作流程配置方案）連到 workflow。以下以 company-managed 服務專案（新版稱 service space）為主。

查看與調整 request form 通常由 space admin 執行；新增 workflow approval step 與官方文件列出的固定核准人設定需要 Jira admin。應按具體操作確認角色，不能因為看得到專案設定，就假定能發布所有共用流程。S01S03S04

04.04.01 找到 request type 真正使用的流程

共用 work type／workflow 時，先確認變更是否會影響其他入口。

先到 Space settings → Request management → Request types，查看目標類型及其 work type／workflow 關聯；再到 Space settings → Workflows 找到對應流程。不要只靠兩個名稱相似就判定相連。

工作流程由狀態和轉換組成，不是頁面上的欄位排序，也不是 board 欄位的同義詞。S01

原創案例中，「借攝影機」和「借收音設備」共用一個 work type。若想只替攝影機新增核准，就先檢查它們是否也共用 workflow。直接編輯共用 workflow，可能連收音設備都開始等待核准。

官方文件建議，特定 request type 需要另一流程時，要先考慮獨立的 work type，避免影響共用者。S01

查看時把每個節點與箭頭讀成一句話：「工作進到待核准；同意後到待交付；拒絕後到已拒絕」。若只有狀態卻沒有想要的箭頭，使用者不會因為看到狀態名稱就有能力跳到那裡。

04.04.02 核准步驟與 portal transition 各解決什麼

Approval step 適合必須取得指定對象同意的決策。設定需要核准人的資料來源、需要多少核准、核准後去哪裡、拒絕後去哪裡；還可指定哪些欄位中的使用者不得成為核准人，例如避免申請人自己核准。只是新增名為「待核准」的狀態或填一個 Approvers 欄位，都不會自動完成整套核准配置。S02S03

在 company-managed 流程中，由 Jira admin 編輯 workflow，選定狀態，啟用 Include approval step，再設定核准來源、門檻與結果。該狀態需要適合核准及拒絕的兩個出口，完成後發布 draft。沒有發布的草稿不應當成已作用於實際工作。

先確認流程不是正式共用流程，才在隔離副本練習。S03

Portal transition 適合讓顧客自助進行「取消」「重新提出協助」等動作。管理員在 workflow 選取轉換，設定 Show transition on the customer portal；

如果只允許特定角色或使用者，還要配置適合的 transition condition（轉換條件）。它的好處是減少單純狀態變更也要等 agent 的情況。S05

重要限制：官方目前明示，portal 轉換不顯示 transition screen，且會忽略該轉換的 validators（驗證器）。因此不能把「必須在轉換畫面填一個欄位」當作 portal 的可靠保護。也不要讓顧客可用的箭頭直接繞過必要核准。

實際要核對條件、可見角色、輸入資料與轉換效果，而不是只測按鈕有沒有出現。S05

04.04.03 預設固定核准人

顯示或隱藏欄位不等於 workflow 已配置核准步驟。

如果所有昂貴設備借用都應由同一組設備管理者核准，就可以預先設定 Approvers 或適合的多使用者／多群組欄位。這能減少每張申請重複選人，但前提是 workflow approval step 真的使用該欄位作為來源。S04

依目前官方文件，由 Jira admin 在 Request types 選目標類型，進到 Request form，把核准欄位加入可用欄位；勾選 Use preset value and hide from portal，填入指定的測試核准人或群組，再儲存。

顧客提交時不選人，agent 在工作項目能看到已設定的核准來源。S04

固定清單解決的是「誰通常負責決策」。它不表示名單中的每個人都是 agent，也不代表誰能看到全部請求。人員可否登入、找到這筆待核准項目與完成核准，仍要按其帳號、專案與請求權限測試。人員離開職務時也要維護這份配置，否則工作可能一直等不存在的責任人。

04.04.04 讓顧客選核准人

如果申請人的主管因部門而異，固定同一人不合適，可以在 request form 放 Approvers 或 user picker（multiple users）欄位，讓顧客選個別核准人。依官方文件，客戶不能用這個方式挑核准群組。

欄位可使用較清楚的 Display name，如「選擇您的核准主管」，並加說明或設成此表單必填。S06

使用此方式前，Customer permissions 必須容許客戶在專案或組織範圍搜尋其他客戶；否則欄位存在但找不到應選的人。這涉及可搜尋對象的範圍，應先審查隱私與服務流程，不為了測試方便隨意開放所有真實人員。S06

允許挑選不代表系統已驗證此人真的是申請者主管。若業務要求「僅直屬主管」或禁止自我核准，要在允許的搜尋範圍、核准排除設定與流程設計中處理，必要時另作超出本課的組織資料整合。不要把任意 user picker 說成完整的主管關係驗證。

隔離練習 相同申請的兩種核准來源

前提：Jira admin 已準備獨立測試 workflow、work type 與核准欄位，沒有正式專案共用。角色為虛構申請人、測試核准人甲與乙、測試 agent。此教材只說明做法，不對真實 Jira 發出變更。

  1. 畫出「收到申請 → 待核准 → 待交付」與「待核准 → 已拒絕」兩條路徑，記錄各箭頭的用途。
  2. 在測試 workflow 的待核准狀態啟用 approval step；設定一位核准即可、來源為測試核准欄位，以及核准／拒絕結果。檢查後由獲權限者發布草稿。
  3. 建立「練習：固定核准」request type，使用 preset value 隱藏核准人，填甲。提交虛構申請，觀察進到待核准後是否由甲可作決定。
  4. 建立另一個「練習：自行選核准人」入口，顯示 Approvers 欄位。先在允許的測試客戶範圍啟用搜尋，再讓申請人選乙，觀察工單的核准來源是否為乙。
  5. 分別用兩張測試申請走「核准」「拒絕」，驗證結果狀態；不要只核對通知信是否寄出。
  6. 若批准練習，新增獨立的「取消申請」portal transition，限制在適當狀態與角色。觀察顧客是否可用、會移到哪個狀態；不設計能跳過待核准直接領取的箭頭。
  7. 測試沒有選核准人、選到不合格對象及未獲授權角色三種負面情境，記錄被哪一層擋下或仍存在什麼缺口。

尚未租戶實測：workflow editor 新舊版入口可能不同；portal transition 的實際可用性與角色條件需在獲准環境確認。涉及共享 workflow 或真實核准通知時停止練習，先取得負責管理員批准。

摘要

先追查 request type 的底層 workflow，再設計核准來源與決策出口。固定核准人適合穩定責任；顧客選人適合案件間差異。Portal transition 提供自助動作，必須檢查是否繞過必要流程。

常見陷阱

  • 把 assignee、Approvers 欄位與真正 approval step 當同一事物
  • 修改共用 workflow 卻只測一個 request type
  • 用 portal transition 的 validator 當唯一資料保護
  • 忘記發布 draft，或把顧客選人當成主管資格驗證

觀念釐清

核准是一個具有來源、門檻與結果的決策機制；轉換是移動狀態的動作。兩者可以配合，但名稱相同的按鈕或狀態不代表相同權限與效果。
