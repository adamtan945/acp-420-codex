02.01 佇列配置與 JQL 排錯

適用範圍、版本用語與案例前提

本課適用 Jira Service Management Cloud，以 company-managed 服務專案為主要情境。新版文件可能寫 service space、work item、work type；考綱仍使用 project、issue、issue type。

教材保留兩套名稱，不把新名稱直接代入 JQL。所有人物、工單和設定數值都是原創教學案例。

佇列是每天的工作清單，不是案件的儲存箱

佇列（queue）讓 agent 把需要注意的請求集中成可操作的清單。每張工作項目仍屬於原本的專案；queue 只是依條件挑出符合的項目。同一張工單可以同時出現在「未指派」、「高優先」和「SLA 快到期」三個 queue，不是被複製了三份。

官方來源：Create a new queue

先備詞彙：filter 是篩選條件；column 是清單顯示欄；JQL（Jira Query Language）是描述「我要找哪些工作項目」的查詢語言；SLA 是量測服務承諾的時間指標；resolution 是結案結果欄位。Queue 讓你看見符合條件的工作；它不會自行完成、指派或改寫那張工作項目。

02.01.01 把團隊需求翻成佇列設計

原創案例：「晨光 IT」的上午分流人員要先看尚未被接手、尚未解決的請求；網路支援組要看 network 標籤；值班主管要看即將超過解決 SLA 的案件。先寫出每一張清單支援的決策，再選欄位。如果決策是「誰要接手」，Assignee 必須清楚；

如果決策是「還有多少時間」，就需要對應 SLA 欄位，而不是只看 Created 日期。

可先設三個 queue：待接手、網路支援、即將逾時。每個 queue 記錄名稱、納入條件、排除條件、顯示欄位和排序。這是本課建議的設計表，不是 Jira 額外要求的一種設定物件。預期效益是讓 agent 少做重複搜尋；它不能替代明確的工作分配責任。

官方來源：Use queues to triage requests for your agents

官方來源：Create a new queue

02.01.02 建立、編輯、排序與驗證

建立 queue 需要 space admin。

從 Queues 旁的 More actions → Queue settings → Create new queue 開始，填寫名稱，在 Filter by 選條件，必要時切 Advanced 輸入 JQL，設定 Order by 和 Columns，再建立。欄位可以拖曳改順序。

建立之後，用相同設定入口選該 queue 編輯；調整群組內 queue 的先後順序則在群組 Manage queues 處完成。

官方來源：Create a new queue

官方來源：Prioritize your queues using groups

先從最窄的條件開始，例如僅看教學專案未解決案件，再逐項增加限制。若一次加入十個條件而結果是零，會難以判定哪一項排除了工單。修改 queue 時，案件本身不會因為從清單消失而被刪除；只是目前不符合條件。要確認，直接用工作項目代碼搜尋它。

02.01.03 Priority groups 與考綱的 Other

Priority groups 是把相關 queue 整理成一組，方便不同團隊聚焦。它不是工單 Priority 欄位，也不會因為 queue 在名為「緊急」的群組，就把所有項目改成最高優先。官方允許同一 queue 加入多個 priority group。

管理員從 Queue settings → Priority group → Create group 建立；再用 Manage queues 選擇與排序該群組的 queue。

官方來源：Prioritize your queues using groups

考綱 V2 April 2025 使用「Priority groups 與 Other」描述。2026-10-05 的目前文件將未加入 priority group 的 queue 放在 View all queues；新舊標籤要並列理解，不能因為看不到 Other 就認為缺少考試功能。

文件也指出 Starred 與 Priority groups 的計數定期更新，View all queues 的計數不是同樣的自動更新行為。因此查異常時要打開清單驗證，不要只相信側邊欄尚未更新的數字。

官方來源：Prioritize your queues using groups

02.01.04 從一行 JQL 開始

ORDER BY 改變排列，不決定哪些單有資格出現。

JQL 最小結構是「欄位＋運算子＋值」。project = TRAIN 表示挑出專案代碼為 TRAIN 的工作項目。這是原創教學專案代碼，並非要求你的網站一定有此專案。AND 代表同時符合，OR 代表符合任一；括號可以把選項範圍組在一起。ORDER BY 只改結果順序，不改符合篩選的集合。

官方來源：Write JQL queries for SLAs

待接手 queue 可用：project = TRAIN AND resolution = Unresolved AND assignee IS EMPTY ORDER BY created ASC。依序讀作：在 TRAIN 中、尚未有結案結果、尚無負責人，再按建立時間由舊到新排列。

若團隊使用特殊工作流程，要驗證 Resolution 確實會在解決時設定、重開時清除；只用狀態名稱判斷未解決可能漏看設定異常。

SLA 欄位名稱有空白時使用雙引號。以該站台已存在的 Time to resolution 為例：project = TRAIN AND "Time to resolution" = breached() 用來找最近 SLA 週期逾時的項目。everBreached() 看是否曾有逾時週期；

paused() 看條件暫停；withinCalendarHours() 看服務行事曆時段。這些函式不是同義詞。

官方來源：Write JQL queries for SLAs

「兩小時內即將逾時、尚未逾時」可以從 project = TRAIN AND resolution = Unresolved AND "Time to resolution" < remaining("2h") AND "Time to resolution" >= remaining("0m") 開始驗證。

Remaining 的負值代表已逾時多久，所以只寫小於兩小時也可能包含已逾時項目；加上非負下界，才符合本案例的「尚未逾時」。這個範例不宣稱所有匹配者此刻都正在營業時間內計時，若需求還要排除 Pause 或日曆外，需另外增加與驗證條件。

官方來源：Write JQL queries for SLAs

這裡教的是篩選已有 SLA 資料；SLA 開始、完成、目標與行事曆如何產生那些資料，由 02.02 說明。不要在 queue 輸入一個不存在的 SLA 名稱，期待查詢自行建立計時器。

02.01.05 查不到、查太多、順序不對，分開處理

查不到已知工單，先用 key = TRAIN-1 確認同一測試 agent 能看見它，再逐項加回原 queue 條件。若工單根本無法開啟，先排查權限及 issue security；若能開啟但不符合 queue，就比對實際欄位值、SLA 名稱及週期。不要用修改權限來修一個標籤拼錯的 JQL。

查出太多工單，檢查括號、OR 範圍、未結案條件與空值。某欄位的「不等於某值」不一定涵蓋沒有值的工作項目；若需求包含空值，必須明確處理。順序不對則檢查 Order by／ORDER BY、排序方向及多欄排序，不要重建整個 queue。欄位沒出現則核對 Columns 配置，以及那張工單是否真的有值。

官方來源：Create a new queue

官方來源：Write JQL queries for SLAs

隔離練習：用四張卡片驗證 queue

需要獨立教學專案、space admin 及 agent 測試帳號。預先準備四張沒有個資的工作項目：A 未解決且未指派；B 未解決且已指派；C 已解決；D 未解決、未指派且有 network 標籤。若要驗證 SLA 查詢，先由 02.02 建立可控的教學 SLA，不能假裝紙上時間就是租戶實測。

  1. 建立「教學待接手」queue，使用未解決且 assignee 為空的條件。加入 Key、Summary、Assignee、Status 及需要的 SLA 欄，先不加多餘欄位
  2. 打開清單。預期 A、D 出現，B、C 不出現。逐張點入核對，不以側邊計數取代驗證
  3. 建立「教學網路」queue，使用 network 標籤。D 可以同時出現在兩個 queue；直接改 D 的 assignee 後，它應離開待接手 queue，但只要 network 標籤仍在，就仍符合網路 queue
  4. 建立「早班分流」priority group，把待接手排在網路之前。核對只是 queue 導覽順序改變，沒有修改 D 的 Priority
  5. 把網路 queue 同時加入另一個測試群組，再切換群組。確認同一 queue 的內容仍由相同篩選條件決定
  6. 故意在教學副本的標籤條件拼錯，練習由已知工單反查。修正後重新查詢，記錄問題的最小原因

這是原創測試矩陣，目的是同時檢驗應出現與不應出現的項目；只看到一張想要的工單，不代表設定正確。

  1. 不需要，這是相同項目的不同篩選結果。2. 不會，群組是 queue 導覽組織。3. 已逾時的 remaining 可以為負值，負值同樣小於兩小時。

重點回顧

Queue 的設計由工作決策出發，再決定集合、欄位與排序。建立後用已知工單做正反向驗證，並把 Priority groups 與工單 Priority 分開理解。

常見陷阱

  • Queue 的消失不等於工單被刪除
  • 最後一輪 breached 與歷史 everBreached 不相同
  • 未加 remaining 下界可能把逾時項目也放進「即將逾時」
  • 側邊計數與實際查詢結果可能有更新時機差異

觀念釐清

Queue 是單一服務專案內的工作篩選；目前另有可跨專案的 Views 能力，屬考綱外的目前產品延伸，不能用它來推論所有 queue 都能跨專案。
