04.03 電子郵件請求管道

有些顧客不知道 portal（客戶入口）在哪裡，只知道寄信給服務團隊。Jira Service Management（JSM）可以把寄到已連接信箱的來信轉成請求。管理員的工作不只是「接上信箱」，還要確定建立哪一種工作、來信能否提供所需資料，以及什麼郵件應被拒絕。

本課用一個隔離測試收件匣示範這三個問題。

基本詞彙與前提

Channel（管道）是請求進入 JSM 的方式，例如 portal、email 或 chat。Request type（請求類型）決定這封信使用的顧客入口配置；work item（工作項目，考綱稱 issue）是建立後交給團隊處理的紀錄。

Email processor（郵件處理器）讀取郵件並處理成請求或回覆。Allowlist（允許清單）與 blocklist（封鎖清單）是郵件過濾設定，不等於 Jira 專案閱讀權限。

以下以 company-managed 服務專案為主。新版稱 service space，較舊的 Project settings 相當於 Space settings。

外部信箱設定需要 Jira admin 或 space admin，信箱提供者還可能要求 Google／Microsoft 管理員同意。不要用私人或正式客服信箱做學習練習，更不能把密碼貼在教材、聊天或工單中。S01

04.03.01 連接自訂信箱

JSM 可使用 Atlassian 提供的收件地址，也能接上既有外部信箱。進入服務專案的 Channels & self service → Email，可查看連接的地址、使用的 request type、Incoming logs 與最後收到郵件的時間。

先確認這真的是要收測試請求的專案，才能開始連線。S01

要加入外部地址，選 Add external email，再選 Google、Microsoft 或 Other。Google／Microsoft 會帶到提供者的驗證流程；由獲授權的人在正式登入頁完成並審查權限。連線成功後檢查 request type。

Other 的連線資料要依當前介面與郵件供應者要求設定，不把某個固定密碼流程當成所有郵件服務的共同做法。S01

連接信箱是一個持續的資料存取安排，因此實務上要先獲得信箱擁有人和管理員的批准。連上之後，應用一封無個資的測試信驗證「收件地址正確、建立到正確專案、內容對應正確、記錄可追查」。看到連線成功只表示第一步完成，不能推論每一封信都會通過身分、過濾和欄位檢查。

04.03.02 選擇 email 能用的 request type

既有必填規則可能阻擋 email；portal 能送不代表 email 能送。

電子郵件的主旨提供 Summary，內文提供 Description。適合 email channel 的 request type 必須讓這兩個欄位可見，其他可見欄位則必須是選填；若再加入無法由信件提供的必填資料，來信可能無法建立工作項目。

Description 系統欄位對此處理流程有必要性，不能從正在供郵件使用的 request type 任意移除。S02

例如 portal 的「借用活動設備」要求活動日期、設備選項與現場地點，適合互動表單；把它直接指定給 email，並不會讓寄信人神奇地填出這三格。較清楚的設計是「電子郵件求助」入口先收摘要與描述，由 agent（服務人員）分流後補足資料。這是原創案例的設計選擇，並非官方規定一定要另建入口。

要更改對應，在 Email 清單找到該地址，選 Actions → Edit，指定合適的 request type 並 Save。用新來信觀察建立結果；不要因為之前的工作項目沒有改類型，就認定設定沒生效。此設定用來決定此後從該地址建立的請求，不是批次重分類工具。S02

若選單看不到預期類型，要檢查它的欄位要求與 Restrictions。現行文件指出，受限制的 request types 不能用於 email channel。把某個類型只允許特定客戶後，不能再假設 email 可以照常使用它。S03

04.03.03 允許與封鎖來源

Allowlist 適合明確信任的寄件網域，用來避免其一般內容被過濾；到 Email → More → Manage allowlist 新增網域，輸入時不加 @。目前僅支援精確網域比對，不支援個別地址、萬用字元或模糊模式。

因此 example.com 不等於 mail.example.com，必須分開思考子網域。S04

不要把官方簡短描述的「總會收到」理解為略過所有安全機制。相同文件明示：若郵件未通過 DMARC 寄件者驗證而被視為詐騙或垃圾信，仍會被過濾。DMARC 是驗證寄件網域身分的一項機制；它不是這門課要深入設定的 DNS 題目，但你需要知道 allowlist 不能保證繞過它。S04

Blocklist 可放網域或指定 email address，適合阻擋某個廣告地址或無關來源。從 Email → More → Manage blocklist 新增，儲存後用合法、獲准的測試寄件者驗證。它也採精確網域比對，不支援萬用字元；

要封鎖 mail.example.com，不能假設封鎖 example.com 已涵蓋。S05

本課不建立同時出現在 allowlist 與 blocklist 的衝突項目，也不編造兩者所有衝突情境的優先順序。遇到衝突先清理重疊設定、看 processing logs，並以當前官方規則核對。郵件清單是接件過濾；customer access、帳號建立、專案存取與寄件者驗證仍需分別檢查。

04.03.04 停用 email requests 的範圍

到 Channels & self service → Email → More actions，選 Disable all email requests，再確認 Turn off。停用後，寄往連接地址的郵件不再由該 email channel 處理，也不會自動轉為工作項目。

這不是單純停止寄給客戶的通知；寄入管道與寄出通知是不同功能。S06

因此切換到 portal-only 服務時，應先通知服務使用者替代入口、確認尚未處理來信的安排，並評估既有案件透過 email 回覆的路徑。這些是變更計畫需要解決的問題，不能把「點了停用」當成服務遷移完成。本課不承諾重新啟用後會如何補處理停用期間的信件；

該行為要依郵件提供者、處理方式與隔離測試結果核對。

隔離練習 小型接件驗收

前提：管理員明確批准隔離專案與專用測試信箱的連線；所有測試寄件者及地址都由你控制，沒有真實客戶或正式郵件。若未獲信箱授權，就只做紙上推演，不登入、不授權連線。

  1. 建立或選用「練習：Email 求助」request type，確認 Summary、Description 可見，其他可見欄位選填，且未套用不相容的入口限制。
  2. 在 Email 加入獲准的測試地址，完成提供者驗證後，檢查它對應上述 request type。
  3. 從測試客戶寄一封「測試：會議室螢幕無訊號」與虛構描述。檢查新工作項目的摘要、描述與 request type，記錄 Incoming logs 的結果。
  4. 在沒有其他使用者的測試副本把額外欄位設為必填，再送一封新測試信。若處理失敗，從 log 找原因後復原欄位，不以重寄大量郵件替代排錯。
  5. 分開測試 allowlist 的精確網域與 blocklist 的指定地址；不要使用真實外部網域做不受控寄信測試。沒有可控制的不同網域，就記錄此案例未實測。
  6. 記下切換前已建立的工作項目，停用測試 email channel，再寄一封全新測試信。預期不會由此管道建立新工作；若仍有紀錄，先核對是否寄到了另一個仍啟用的地址或由其他 automation 建立。
  7. 依練習環境負責人的批准恢復原設定。恢復後再測一封新信，對停用期間信件另作記錄，不自行假設會補建。

  2. 不是，目前採精確網域比對。

摘要

電子郵件接件需同時配置連線、合適的 request type 與寄件過濾。排錯先找處理記錄與欄位條件，再檢查顯示工單的 queue；停用管道前要確認替代服務方式。

常見陷阱

  • 把含額外必填題目的 portal 入口直接指定給 email
  • 把 allowlist 當成略過 DMARC 或客戶存取要求
  • 假設網域規則會自動比對所有子網域
  • 把停用寄入 email 當成停用寄出通知

觀念釐清

「收到信箱」「JSM 處理成功」「建立出工作項目」「出現在某個 queue」是不同觀察點；應依實際紀錄定位問題，避免只用最後畫面猜根本原因。
