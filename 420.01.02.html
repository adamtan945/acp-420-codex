01.02 客戶、組織與請求分享

本課適用 Jira Service Management Cloud，以 company-managed 服務專案為主要情境。新版文件可能寫 service space、work item、work type；考綱仍使用 project、issue、issue type。教材保留兩套名稱，不把新名稱直接代入 JQL。所有人物、工單和設定數值都是原創教學案例。

為什麼「讓客戶進來」和「讓客戶彼此看見」要分開設計？

服務入口可以像開放的服務台，也可以只服務一群已受邀的人。但能走進服務台，不代表能翻閱別人的案件。這一課把三個問題拆開：誰能建立帳號、誰能送請求、誰能分享請求。最後才處理客戶背景資料。這個順序能避免為了方便登錄資料，意外開放整個入口。

先備詞彙：help center 是可集合多個服務入口的求助中心；portal 是某服務專案面向客戶的入口；channel 是請求進來的管道，例如 portal、email 或 widget；organization 是用來集合客戶的組織。Detail field 是客戶或組織檔案上的背景欄位，不是每張請求各自填寫的 Jira 欄位。

01.02.01 客戶註冊：網站先決定邊界，專案再決定接納誰

網站層 customer access 決定內部與外部客戶帳號能如何建立，以及求助中心是否要求先登入。專案管理員的 customer permissions 在這個邊界內控制入口使用者。因此，只把專案 Channel access 改為 Open，不能推論網站所有帳號建立限制都已取消；反過來，網站允許自行註冊，也不代表每個 portal 都對所有客戶開放。 官方來源：How customer access settings impact project permissions

原創案例是「晨光維護服務」：公開提供使用說明，但只有受邀的測試合作館可以提交保固請求。可採網站允許造訪公開 help center，專案設 Restricted。對外部人員而言，閱讀說明、建立帳號、提交指定服務的請求，是三個可分別驗證的動作，不應合成一個「能登入」測試。

需要管理網站 customer access 時，找具網站管理權的管理員；只需調整單一服務專案的 customer permissions 時，由 space admin 操作。不要為了修改一個 portal 就授予整個組織的管理權。 官方來源：How customer access settings impact project permissions 官方來源：Change service space customer permissions

教學客戶與組織如何加入

在獨立教學專案，agent 或 admin 可從 Customers → Customers 分頁 → Add customers 加入專用測試帳號。這個動作可能寄出邀請或驗證信，即使停用 Customer invited 通知，也不能推論完全不會寄 email；所以先確認收件者為核准測試收件匣。 官方來源：Add a customer to a service space

建立教學組織時，從 Customers → Organizations → Add organization，輸入新名稱或選既有教學組織後 Add。要把測試客戶放入其中，點組織名稱 → Add customers → 指定帳號 → Add。組織可以用於多個服務專案，成員異動的影響可能超過目前開啟的專案；請使用專用教學組織。Agents 是否可以管理這些組織與成員，還取決於 JSM Configuration 中 Organization management 的授權設定，不能只看 agent 身分。 官方來源：Add an organization to a service space 官方來源：Add a customer to an organization

01.02.02 不用先登入，不代表永久匿名追蹤案件

官方文件中的免登入提交情境，需在網站 customer access 允許客戶建立帳號，並開啟 Customers can access and send requests from the portal without logging in，再由適當專案開放 Channel access。提交時仍會要求 email，系統建立帳號；客戶後續要查看請求時仍需要完成帳號及登入步驟。因此「免登入送出」和「任何人可匿名閱讀私人請求」完全是不同能力。 官方來源：How customer access settings impact project permissions

教學時不應把這個選項直接套用到醫療、人事或法務服務。學會設定不代表應該啟用；先判定請求資料的敏感程度、服務對象與組織政策。這是設定前的風險判斷，不是額外的考試功能。

01.02.03 Channel access 與 Customer sharing 的操作及影響

從服務專案進入 Space settings → Access → Customer permissions，先設定 Channel access，再設定 Customer sharing，最後 Save。Open 會依網站客戶存取設定決定哪些人可使用；Restricted 則讓已由 agent 或 admin 直接邀請到此服務專案的客戶提交 portal／email 請求。 官方來源：Change service space customer permissions

Sharing 有三種主要選擇：只搜尋自己組織內的客戶；可搜尋組織內客戶並手動輸入專案內其他客戶的 email；或可搜尋整個專案／組織的客戶。它們影響的是「能找誰、能把請求分享給誰」。若網站也允許新客戶帳號，某些以 email 分享的組合還可能邀請新客戶，不能只把它當成搜尋框的外觀選項。 官方來源：Change service space customer permissions

假設測試客戶 A、B 在「北館」組織，C 在「南館」。只允許組織內搜尋時，A 可搜尋 B；不能因此推論 A 可搜尋 C。A 沒把私人請求分享給組織或 B 之前，也不能僅由組織成員關係推論 B 已取得該請求。請用獨立登入驗證「搜尋得到」和「實際看得到案件」兩件事。 官方來源：access-troubleshoot

目前官方文件有重要例外：Channel access 並不限制 Slack 或 Microsoft Teams 的 chat 提交；透過 chat 送出請求的使用者可自動受邀到服務專案。需要封閉所有請求管道時，要另外稽核 chat 的連接與設定，不能把 Restricted 描述為所有管道的萬用封鎖。 官方來源：Change service space customer permissions

01.02.04 客戶與組織詳細欄位：資料定義和資料值分開管理

客戶詳細欄位可以記錄該客戶的背景，例如「教學偏好語言」；組織詳細欄位可記錄整個客戶組織的背景，例如「教學服務區」。當 agent 開案件時，這類脈絡可減少反覆詢問。欄位定義是名稱、類型和可查看／編輯的人；欄位值是某位客戶實際填入的內容。改一位客戶的值，不等於改全站欄位定義。 官方來源：Manage customer detail fields 官方來源：Manage organization detail fields

必讀版本說明：考綱 V2 April 2025 仍以 JSM 客戶／組織詳細欄位命題。Service Collection 於 2025 年 10 月推出後，新網站的這些 customer-service 功能移到 Customer Service Management（CSM）。舊網站可能仍保有 JSM 入口；新網站看不到 Manage details，不能直接判斷為權限錯誤。本課先教考綱概念，以下路徑只適用仍提供該 JSM 功能的環境。 官方來源：Manage customer detail fields 官方來源：Manage organization detail fields

在適用環境中，Organization admin 或 Jira admin 可建立客戶欄位；agent 可依欄位權限維護客戶資料。Customers → Customers 分頁 → Manage details → Manage detail fields → Create field 可定義客戶欄位。組織欄位則從 Customers → Organizations 分頁進入相應入口。選好標籤、類型與查看／編輯對象再建立。新增欄位定義影響 JSM 全體客戶或全體組織，不僅目前專案。 官方來源：Manage customer detail fields 官方來源：Manage organization detail fields

類型要在建立前想清楚：單選適合「只選一個服務區」，多選適合「支援語言可多個」，日期適合到期日，文字適合自由描述。官方文件指出既有 detail field 不能直接改類型；刪除欄位會連同相關資料移除。這也是為何練習不要建立真實個資欄位、不要把刪除當成隨便重設。 官方來源：Manage customer detail fields 官方來源：Manage organization detail fields

隔離練習：受邀館舍支援台

先備條件：獨立教學網站，已核准的測試帳號 A、B、C、space admin；網站層變更由已授權管理員執行。任何可寄出邀請的動作只使用專用測試收件匣。沒有可用 JSM detail fields 的環境，就用相同資料的紙上卡片完成最後兩步，並記錄產品差異。

  1. 在紙上先寫需求：「僅受邀者可以從 portal 送請求；A 和 B 能在北館內搜尋彼此；C 不在北館」
  2. 讀取網站 Customer access，記錄是否允許自行註冊及免登入。這一步先讀，不任意修改全站設定
  3. 在教學專案 Customer permissions 選 Restricted，Customer sharing 選組織內搜尋，儲存
  4. 將 A、B 放入測試北館，C 放入測試南館；不要用真實網域自動歸戶。分別登入三個帳號，確認受邀提交可行，且跨組織搜尋符合限制
  5. 讓 A 提交一張私人請求，再由 A 分享給 B。比較分享前後 B 的請求清單，記錄可見性變化；另保留一張未分享請求做對照
  6. 由有權管理員在適用 JSM 環境建立「教學偏好語言」單選欄位，設定只有教學服務團隊可編輯；agent 為 A 設值「繁體中文」。檢查 B 有同一欄位定義，但沒有被自動填成 A 的值
  7. 建立「教學服務區」組織欄位，為北館填「北區」。檢查南館有欄位而值可不同。把欄位標籤改名時，觀察所有組織皆使用新標籤

預期結果是能提出請求、能找分享對象、能看已分享請求、能維護背景資料四項各自成立。若任何一項失敗，先回到它所屬的設定層，不要一次放寬全部權限。 官方來源：Change service space customer permissions 官方來源：Manage customer detail fields 官方來源：Manage organization detail fields

重點回顧

先決定網站註冊與登入，再設定服務專案的請求管道與分享；每一步都用不同測試帳號驗證。客戶與組織 detail fields 是背景資料，定義可跨專案影響多人。

常見陷阱

  • Restricted 不等於已封鎖 chat 管道
  • 免登入提交不等於匿名查看私人請求
  • 修改 detail field 的名稱／類型設計，和修改某個人的資料值，影響範圍不同

觀念釐清

網站層 customer access 是各專案的可用邊界；專案 customer permissions 是在邊界內決定如何服務。二者不是重複的同一個開關。

文件限制與待實機核對

此課未測試任何租戶的邀請郵件、chat 自動邀請或 CSM 遷移畫面。站台身分管理方式與 rollout 可能影響入口；若入口不同，先辨識產品與管理角色，再依當前官方文件尋找等價設定。
