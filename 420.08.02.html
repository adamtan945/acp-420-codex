08.02 從事件到結果 建立JSM自動化規則

認證：ACP-420｜考綱：V2 April2025｜Automation 11%｜查核：2026-10-05 覆蓋：08.02.01–08.02.27。這一目標細項較多，按「骨架、JSM元件、資料、維護」四段完整閱讀；正式教材可分多個獨立HTML小節，但不能省去細項。

先看骨架

Trigger讓規則開始；condition決定是否繼續；action做事；branch把處理上下文帶到指定的關聯對象。想像一張包裹進站：事件是收到包裹，條件是目的地符合，動作是貼標籤或指派配送，branch則是對包裹內的各件物品分別處理。

名稱相似不代表用途相同。Condition「有附表單」不能取代trigger「表單已提交」；建立工單的動作也不會自動把後面的上下文改成新工單。這是初學者最需要先理解的順序與對象。建立規則、關聯工作分支

從空白、範本或AI開始

在目前Cloud文件中，進入服務space的Space settings → Automation，選Create flow，可從空白、template或Rovo建立。範本能提供骨架，不能知道你的實際欄位、收件者和權限；套用後逐一確認，不直接開啟到production。

從空白的安全練習順序：選一個獲准的示範專案，建立清楚命名的規則，加入trigger，再放condition和action，設定owner／actor，先使用測試資料與可觀察的日誌輸出。啟用後真的觸發一次，再到audit log核對結果。實作使用者必須具相應管理權限；跨多專案scope還需要全域層級的管理能力。目前建立流程、設定與範圍

Rovo可依自然語言產生規則，但生成後仍要查trigger、條件、動作、scope和recipient。考綱稱Atlassian Intelligence，不代表每個現在的AI入口仍顯示舊名稱。先預覽再檢查，沒有把握的動作保持停用。Rovo建立自動化

自動解決、關閉與提醒

「三天沒有新回覆就關閉」不是單一按鈕。你需要說清楚什麼時間欄位代表沒有新回覆、哪種請求適用、目前狀態允不允許轉換、以及是否要先提醒顧客。使用排程或適合的事件，搭配JQL限定對象，再以transition動作走工作流程允許的路徑。

不要把Resolved、Closed、Done和Resolution當同一個東西。狀態由流程定義，Resolution是另一個欄位；若服務要求已解決後才關閉，要確認轉換與欄位值都符合預期。若希望寄提醒，另外配置通知action與內容，不要只在規則名稱寫「提醒」。

Agent手動可以做的轉換，不代表actor也可以。測試時檢查actor的權限與workflow條件；不要因為失敗就把所有人的權限放大。自動化轉換、actor

五種考綱指定的JSM觸發器

  1. Approval completed：核准步驟已被接受或拒絕。它不是「開始等核准」
  2. Approval required：需要核准的情境發生或相關核准資料更新，適合安排待核准流程
  3. Object created／updated／deleted：Assets物件事件。官方目前要求全域automation使用Object trigger；不要直接放進僅支援專案表單的設計
  4. SLA threshold breached：在指定SLA違反或接近違反門檻時啟動，時間點依配置而定
  5. Form submitted：表單提交事件。考綱常用Forms submitted舊名；目前文件指出只支援space-specific。多選表單時要仔細核對，文件說所有選取表單皆提交才觸發，不是任一表單

選trigger應依「何時開始」決定，不能用名稱聽起來相近的事件代替。JSM與Forms觸發器

三種考綱指定的條件

Affected services condition：看工單受影響服務的名稱、tier或相依服務是否符合。先確認工作類型真的包含對應欄位。

Forms attached condition：檢查附加表單及狀態，不會自己等待未來有人提交。表單相關步驟受專案範圍限制；不要把它當可隨意放入任何global flow的元件。

AQL condition：以Assets Query Language檢查物件或資產欄位。JQL主要查Jira工作，AQL查Assets資料，不能互換。語法驗證通過只代表格式可接受，不保證一定有匹配物件。

幾個必須弄清楚的差別

Edit request type不會任意重建底層工作類型。若選的request type和工單work type不相容，可能失敗；先檢查04.01的對應關係。Request types與work types

Lookup objects是取得集合，並不是自動把每筆設成可編輯上下文。當後續要改物件，按目前官方限制使用Object trigger的物件或AQL branch等適當方式。單純在Lookup後直接加Edit object，不應假設一定可行。針對工單Assets欄位的參照更新，又是另一種操作；欄位指到新物件和物件本身改屬性必須分開。Cloud屬性更新案例、更新工單Assets欄位

Approve／decline request會對目前核准程序作決定；不是只通知某人。正式環境若用它，必須有明確業務政策，不能讓任意請求繞過人工審核。教學不提供一鍵核准真實工單的功能。

Form動作亦不是普通檔案複製。Attach／Copy會處理表單及其上下文，範圍和來源工單要逐一核對。表單是否可編輯、是否已提交與是否已鎖定，須回到04.02的狀態設定。Forms使用方式

動作的操作練習卡

下列是原創的隔離練習設計。共通入口是規則編輯器新增action；先有合法trigger與適用scope，再設定要處理的對象。每張練習卡都列「輸入→效果→驗證」，而不是只要求找到按鈕。未經授權，不在正式網站執行。

Assets action 與 Edit Assets field attributes

輸入是測試工單上已參照的資產及其目標屬性。先確認欄位不是空的、物件就是預期那一件，再選要改的屬性與符合型別的測試值。效果應出現在資產物件的資料，而不只是工單summary。驗證時同時看工單參照與物件詳情；如果動作欄位留空會清除值，不能把空白一律當成「不修改」。

Add service project customer

新版名稱可能顯示Add service space customer。在隔離環境使用獲准的測試身分，選目標服務空間，再依需求決定是否加入已存在的測試organization。效果是顧客資料與服務關係，沒有因此授予agent或管理員資格。驗證顧客清單與組織歸屬，再測適當入口；不要用一串重複呼叫代替等待資料可搜尋，新增後短時間查詢可能尚未反映。

Create incident

先準備可用的incident request type及必要欄位，選目標服務空間和該類型，填虛構摘要。效果是新建事件請求；不等於把觸發工單本身轉成incident。若元件提供避免重複建立開啟事件的選項，依需求明確設定。驗證新key、request type、必要欄位與既有工單的關係。

Edit request type

準備一張測試請求與兩個共用相容work type的request type。選目標類型，執行後查看同一key上的request type及顧客呈現；再以不相容類型做設計檢查，不要在production試錯。若目的是改底層work type，這個動作不是任意搬移／轉型工具。

Approve／decline request

僅在虛構且確實處於pending approval的測試請求上理解此操作：它會作成該步驟的接受或拒絕決定，不能當成「幫某一位核准人按送提醒」。文件特別說明其效果不取決於流程還需要幾位核准人，因此業務控制要先確認。驗證核准紀錄及後續workflow結果，不以寄信紀錄代替。

Create work item with a request type

選目標服務空間、request type及可設定的必要欄位，使用明確虛構資料建立。驗證新工單有正確的request type，且是你預期的顧客服務情境。動作可用欄位不等於任意Jira欄位；hidden fields有文件列出的限制。若顧客入口依隱藏預設值工作，不能直接推定自動化建立的行為完全相同。

Create object

使用管理員已備妥的測試schema及object type，選屬性並給符合型別的值。效果是新增資產物件，不是新增Jira工單。驗證新物件、屬性及所屬type，並避免測試反覆建立無法辨認的副本。這是08.02的自動化用例，不會把03.01擴張為從零設計schema的課程。

Lookup objects

在既有測試schema中，以AQL找一組已知物件。先檢查查詢是否找到正反測試資料，再用日誌顯示不敏感的識別資訊。效果是得到結果集合，不是修改物件或開啟branch。零筆、一筆及多筆都應測試，後續動作要能處理結果數量，不能只靠第一筆剛好正確。

Edit object

先確認目前處於官方支援的物件上下文，例如Object trigger，或合適的AQL branch。選屬性與值，執行後比較該物件前後變化；不要只看Lookup的數字。若型別不合或上下文不對，就回頭修設計，不用改成不受限的管理身分來掩蓋。

Attach forms

在space-specific規則中選取示範表單，確認作用工單與表單可見性。效果是附上表單，還沒替人完成內容或提交。執行後檢查Forms區塊、顧客／內部可見範圍與表單狀態。不要把「附加」和「提交」當成同一個事件。

Copy forms

明確選來源工作項目與要複製的表單，確認目前工單為目標，再用兩張虛構請求測試。執行後核對目標的表單內容、狀態和可見性，避免把含內部資訊的表單傳到不適合的請求。這類form action也須注意space-specific限制；實際複製結果按目前元件選項與隔離測試核對。

操作規則與限制來源：Cloud動作參考。以上具體練習資料及驗證順序是教學設計；每張卡都要配合前文的角色、scope與audit驗證。

Branch改變目前處理的工單

假設請求A產生了後續工單B。若你在Create work item後直接加Comment，主流程的目前工單通常仍是觸發者A，不是新建立的B。要對新工單處理，使用適當的關聯工作分支。

在相關工單branch內，{{issue}}指目前該分支的工單；需要原觸發者時可用{{triggerIssue}}。多工單branch可能並行，不能依賴前一條branch先完成再給下一條讀取結果。也不要把branch內建立的變數當成全流程任何位置都可用。

這些原則同時說明為什麼流程圖要標「現在處理誰」，而不能只畫一串箭頭。Branch上下文、順序與隔離

Smart values 五種資料的讀法

Smart value是執行時替換為資料的占位表示法。雙大括號包住的是資料路徑或運算，文字看起來像欄位並不代表它一定存在。

  • String：例如{{issue.summary}}取得摘要。要截取或比對文字，先確認是文字類型。文字方法
  • List：多選欄位與查詢可能回傳清單，需要逐項迭代、取得數量或連接顯示；不要把清單當一個人。清單方法
  • Date：日期需注意解析、格式與時區。例如現在時間的顯示形式和實際值是兩回事。日期時間
  • Number：算術前確認資料能轉成數字，避免將文字拼接當數值相加。數學運算
  • Variable：保存中間值供後續使用，但Create variable的結果有型別與分支可見範圍限制；需要數字或日期運算時先確認轉換。Smart values總覽

練習先用Log action輸出一個簡單值，再加入一層轉換，最後才用在寄信或編輯欄位。不要一次串五個方法，出錯時卻不知道哪一段空了。UI把issue改稱work item，不代表{{issue}}要跟著改字。smart value排錯

實際測試日期列時，先Log目前{{now}}，再Log加兩日的值，用真正的輸入算出當次預期，不強求永遠輸出表中的示例日期。若刻意把hoursText改成twelve，asNumber不能成功轉為12；應先驗證與處理不能轉換的輸入，不把失敗當零。

建議操作順序：建立只作用於測試工單的Manual trigger；先放一個Log輸出摘要；加入清單兩列；加入日期原值與轉換值；加入Create variable和數學Log；核對每列結果；完成後停用。若某列空白，就退回原始值檢查，別一次調整所有語法。Create variable必須排在使用它的動作之前；若建在branch內，不能假設主流程也能讀到。

來源：文字與asNumber、清單size／join、日期運算與格式、數學表示式、Create variable型別、分支隔離

開關、分類與維護

儲存、啟用及更新不是永遠同一個動作。規則停用時不會對新事件執行；已啟用規則修改後還要依介面保存更新。完成示範後停用測試規則，避免後續測試資料又觸發。建立與啟停

Labels用來組織規則，例如notification、asset-return；它們方便管理頁搜尋，不會自動成為規則條件。若想只處理某類工單，需要在規則裡設定相應condition。規則labels

完整原創案例 表單提交後提醒內部審查

需求：隔離示範專案的「設備驗收」表單提交後，若工單仍在Awaiting review，加入一則供內部人員看的提醒。這個案例刻意不寄外部信、不改真實Assets物件，也不自動核准。

  1. 確認測試工單、已附的指定表單和Awaiting review狀態都存在
  2. 建立space-specific規則；選Form submitted並限定該表單
  3. 加入status條件，避免已完成工單也被重複提醒
  4. 加入內部留言動作，內容指明表單名稱及待辦；確認comment visibility不是顧客可見
  5. 設定合理actor、owner及清楚名稱，核對scope後啟用
  6. 提交指定表單，確認只有預期的工單出現內部留言及audit紀錄
  7. 再提交另一張不符合狀態的測試工單，確認規則略過；測試完停用

此案例用到08.02的trigger、condition、action、範圍及啟停。若真實需求還要再寄信或更新資產，先獨立驗證下一個動作，不把所有副作用一次加入。表單提交通知的Cloud案例

自我檢查

問題：建立B工單後下一步留言出現在A，先查什麼？

查看答案與理由

查看目前上下文及是否建立適當branch，不先重建留言action或提高權限。

摘要

選事件、加條件、對正確上下文做動作；依需求使用branch。JSM專有元件涉及核准、SLA、Assets與Forms，scope並非全部相同。Smart values要核對型別和上下文。範本與AI都要審查，啟用後用audit確認。

常見陷阱

把Form與Object元件硬放同一scope、把Lookup當branch、以為建立新工單會切換上下文、把label當condition、把範本完成當成驗證完成、未檢查權限就用自動核准。
